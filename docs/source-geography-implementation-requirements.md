# Требования к реализации географии поиска для одного источника

## Назначение

Документ задаёт обязательные правила для ассистента, который дорабатывает один источник вакансий. Для каждого источника ассистент составляет отдельный план, получает его одобрение пользователем, реализует согласованное поведение и подтверждает его живым поиском через движок приложения.

Документ применяется повторно для каждой доработки. Он не разрешает начать реализацию конкретного источника без ревью его плана. Изменения общего контракта, состава поддерживаемых вариантов сайта и точности поиска также проходят согласование.

**Источник** — отдельный ресурс или адаптер карьерной платформы. **ATS** — система управления наймом, которая предоставляет карьерные доски разным работодателям. **Доска** — конкретный сайт вакансий работодателя, со своими настройками и значениями фильтров.

**Нативная география поиска** — условие, которое поисковый сервер источника получает до выдачи вакансий и применяет к составу ответа. **Конвертер** — код преобразования общего географического ввода приложения в допустимые параметры этого источника. **Постфильтрация** — проверка и отсев уже полученных вакансий; она находится вне области этой работы.

## 1. Область работы и приоритеты

1. Дорабатывается путь от географии сохранённого пользовательского брифа до фактически отправленного поискового запроса источнику, включая получение необходимых справочников и следующие страницы выдачи.
2. Реальные возможности и ограничения ресурса определяют функциональность адаптера. Старый аудит, предыдущая таблица, план и предположение ассистента не заменяют проверку действующего ресурса.
3. Если ресурс не поддерживает нужное ограничение, это объявляется явно. Запрещено изображать поддержку добавлением игнорируемого параметра, скрытым расширением географии или последующим отсевом результатов.
4. Парсинг географии из текста вакансии, улучшение локального отбора и проверка доступности удалёнки по описанию не входят в задачу. Наличие города в ответе само по себе не доказывает геофильтр поиска.
5. Место офиса, административный город, радиус вокруг точки, регион работодателя и территория допустимой удалённой работы имеют разный смысл. Подмена одного другим допускается только как явно описанное ограничение, согласованное пользователем.

Подготовка справочника до запроса не является постфильтрацией. Если справочник мест можно получить только из полной ленты вакансий, ассистент фиксирует эту зависимость и её стоимость в плане: необходимость полного обхода нельзя скрывать под названием «справочник».

## 2. Обязательный порядок работы и ревью плана

| Этап | Обязательный результат | Условие перехода |
|---|---|---|
| Исследование | Текущий ввод приложения, действующие API и формы источника, проверенные ограничения и доказательства | Для ATS исследованы минимум 10 разных компаний |
| План одного источника | Способ перевода, границы поддержки, размещение кода, объявления возможностей, тест-кейсы и команды живой проверки | План передан пользователю на ревью |
| Согласование | Явное одобрение показанного плана пользователем | Только после одобрения начинается реализация |
| Реализация | Изменения в рамках согласованного плана | Выполнены необходимые проверки кода и подготовлен живой прогон |
| Живая приёмка | Поиск через штатные сервисы и движок, реальные запросы источнику, сравнение с ожидаемым поведением | Все обязательные случаи подтверждены, ограничения отражены в результате |
| Передача | Отчёт с изменениями, командами, доказательствами, статусом и оставшимися ограничениями | Заявление о готовности соответствует фактической проверке |

До одобрения разрешены чтение кода и документации, просмотр сайта и диагностические поисковые запросы. Небольшие исследовательские скрипты допустимы как средство проверки; они не должны незаметно превращаться в производственную реализацию.

Одобрение плана нельзя выводить из отсутствия ответа, истечения времени или общего интереса к задаче. Существенное расхождение с реальными возможностями, изменение точности, новое общее API или расширение области работ требуют обновить план и снова получить одобрение до зависимых изменений. Незатронутые одобренные действия можно продолжать.

### Когда и как эскалировать

Ассистент обращается к пользователю, если не установлен надёжный способ автоматического сопоставления, не хватает данных для различения мест, источник даёт только более широкую категорию, нужен новый общий справочник или невозможно выполнить условия живой проверки.

Эскалация должна содержать:

- конкретный пример входа и наблюдаемое ограничение источника;
- проверенные запросы или поля, на которых основан вывод;
- варианты решения и их последствия для точности, охвата, стоимости и поддержки;
- рекомендацию ассистента и решение, которое требуется от пользователя.

Варианты могут включать получение дополнительного справочника, выбор места пользователем, согласованное широкое ограничение или явное отсутствие поддержки. Запрещено выбирать ослабление условия молча. Независимо от наличия затруднений план каждого источника обязательно проходит ревью пользователя.

## 3. Проверка реальных возможностей источника

Перед планированием реализации ассистент обязан изучить текущий поисковый API и реальный интерфейс сайта: видимые и скрытые поля формы, динамические меню, сетевые запросы при выборе географии и переходах между страницами. Документация сопоставляется с работающим публичным маршрутом, который будет использовать адаптер.

Для каждого заявляемого географического фильтра фиксируются:

| Что проверить | Что должно быть установлено |
|---|---|
| Вариант доступа | Точный публичный маршрут и версия интерфейса; необходимые условия доступа |
| Параметр | Имя, тип, сериализация, допустимые значения, зависимость от других полей |
| Значение географии | Страна, город, офис, группа, радиус или другой установленный смысл |
| Источник значений | API справочника, форма, данные страницы или другой проверенный механизм |
| Серверное применение | Изменение состава ответа на реальное допустимое ограничение |
| Отрицательный контроль | Реакция на невозможное значение: ошибка, пустая выдача, игнорирование или сброс фильтра |
| Пагинация | Сохранение параметров и их смысла на следующих страницах |
| Полнота справочника | Все варианты доски, только текущая страница, только активные вакансии или другое ограничение |
| Граница доступа | Публичный поиск и API аккаунта работодателя не подменяют друг друга |

Минимальная исследовательская проверка сравнивает запрос без географии, запрос с существующим значением и запрос с заведомо невозможным значением. При необходимости добавляются второй существующий город и контроль другого работающего серверного фильтра. Диагностическая передача невозможного ID допустима при исследовании контракта; она не подменяет пользовательский ввод в приёмочном прогоне.

Сравниваются идентификаторы вакансий, поля ответа и возвращённые сервером итоги. HTTP 200, выбранная подпись, изменение URL, сокращение DOM в браузере и один пустой ответ сами по себе не доказывают серверный геопоиск. Для малой доски, где все вакансии в одном городе, нужен дополнительный различающий случай.

Если сайт выполняет фильтрацию в браузере после получения полной ленты, этот факт отражается как отсутствие нативного ограничения для исследованного HTTP-маршрута. Нельзя переносить параметр состояния интерфейса в API без проверки его действия.

### Для ATS: минимум 10 компаний

1. Выбрать минимум 10 разных работодателей на этой ATS. Десять URL одного работодателя и десять снимков одной доски не заменяют десять компаний.
2. Составить матрицу компаний: URL, вариант интерфейса, страны и города, доступные поля, способ получения значений, ожидаемые особенности.
3. По возможности включить разные страны, языки, размеры ленты и настройки географии, в том числе несколько мест у вакансии и отсутствие нужного поля. Отсутствующее в реальной выборке разнообразие не выдумывается.
4. Для каждой выбранной компании проверить действующий контракт и выполнить предусмотренные ей случаи живого поиска. Положительная поддержка фильтра должна подтверждаться различающими результатами; одни пустые ленты этого не доказывают.
5. Недоступная доска не засчитывается как успешно проверенная: она заменяется другой либо становится предметом эскалации. Если доступно меньше 10 компаний, ассистент сообщает об этом и предлагает варианты; сам не уменьшает порог.
6. Отличия интерфейсов или настроек отражаются в возможностях конкретной доски. Единая ATS не гарантирует одинаковые имена полей, ID офисов, справочники или семантику фильтров.

Полное произведение всех тестов и всех компаний не обязательно. План должен заранее распределить случаи по матрице так, чтобы каждая компания участвовала в живом поиске, базовые условия были проверены на всех применимых досках, а каждый выявленный вариант контракта имел собственную проверку.

## 4. Требования к автоматическому конвертеру

### Вход и полнота обработки

Входом служит общий формат приложения. Конвертер не требует, чтобы пользователь или вызывающий ассистент заранее знал ID, метки или коды конкретного сайта.

На момент подготовки документа текущий путь ввода определяется `src/web/static/location-editor.js`, `SearchPlace` в `src/models/filters.py` и `BriefService.normalize` в `src/services/briefs.py`:

- сохраняются от 1 до 5 разных мест;
- `scope=country` обозначает всю выбранную страну с её ISO-кодом;
- `scope=city` содержит выбранный `geoname_id`, страну, подпись и административное уточнение;
- сервис брифа проверяет выбор и нормализует название города; отображаемая подпись и идентичность места сохраняют разные роли;
- у каждого места могут быть собственные условия формата работы и помощи с релокацией.

Перед работой эти факты перепроверяются по текущему коду. Более широкий технический лимит поля модели не заменяет контракт формы и сервиса брифа. Нельзя сузить каталог фронта, убрать допустимые страны или требовать английский ввод ради прохождения конвертера.

**Полнота конвертера означает определённый результат для любого допустимого ввода фронта. Она не означает, что ресурс способен точно отфильтровать любое место мира.** Если точное выражение невозможно, конвертер возвращает установленную причину и степень поддержки, а поведение поиска определяется согласованным планом.

### Получение и сопоставление значений

- Значения берутся автоматически из действующего справочника источника, формы, данных страницы либо из общего географического справочника с установленным происхождением.
- Запрещены вручную написанные таблицы «город/страна → ID/название источника», цепочки условий для известных городов и такие же таблицы, вынесенные из кода в JSON или настройки.
- Имена HTTP-параметров, структура JSON и правила сериализации являются кодом контракта. Они не дают разрешения зашить географические соответствия. Примеры ID допустимы в тестовых данных и доказательствах, но не как производственный способ разрешения мест.
- Допустим автоматически полученный кеш справочника или результатов сопоставления. У него должны быть происхождение, область действия, время получения и правило обновления; кеш не должен превращаться в вручную сопровождаемую таблицу.
- Сопоставление учитывает страну, идентичность города, административное уточнение, доступные алиасы и данные источника. Транслитерация, первое совпадение или наиболее населённый город сами по себе недостаточны.
- Неоднозначность и отсутствие места обрабатываются явно. Предположение модели без проверяемого основания не считается установленным соответствием.
- Значения конкретной доски не переносятся между работодателями без доказательства общей области идентификаторов. Кеш разделяет источник, работодателя, вариант и язык там, где от них зависят значения.
- Поведение на пустом кеше и после его обновления должно сохранять смысл. Устаревший ID, исчезнувшая локация и сброшенный сервером фильтр не должны молча превращать точный запрос в широкий.
- Если справочник показывает только места активных вакансий, отсутствие города в нём не объявляется доказанным «0 вакансий» без установленной полноты и семантики этого механизма.

Для страны целиком проверяется именно охват страны. Перечисление известных городов допустимо только с доказанной областью покрытия; вакансии без города и условия удалённой работы нельзя терять молча. Выбор страны вместе с городом должен сохранять связь этой пары: сочетание двух независимых фильтров не всегда доказывает один адрес у многолокационной вакансии.

### Результат подготовки

По каждому выбранному месту должны быть доступны исходный выбор, найденное соответствие, происхождение значений, применённые параметры и один из следующих смысловых результатов. Точные имена полей утверждаются в плане общего контракта.

| Результат | Значение |
|---|---|
| Точно выражено | Нативный параметр выражает согласованный смысл выбранного места |
| Выражено шире | Получается регион, группа, радиус или иное более широкое ограничение |
| Не поддерживается | У исследованного варианта источника нет нужного нативного ограничения |
| Неоднозначно | Остаются несколько допустимых соответствий, выбрать автоматически нельзя |
| Соответствие не найдено | Нужный вариант не найден в доступных данных; это не автоматически пустая поисковая выдача |
| Ошибка подготовки | Справочник, транспорт или ответ не позволили выполнить разрешение места |

Пользовательский выбор, ограничение источника и техническая ошибка не смешиваются в один результат. Для всех результатов, кроме точного, план определяет поведение запуска: запрос решения пользователя, пропуск соответствующей ветви либо явно разрешённый широкий запрос. Ассистент не выбирает это поведение заново во время реализации.

## 5. Размещение кода и границы ответственности

Весь код, специфичный для преобразования географии конкретного источника, располагается рядом с его адаптером в отдельном подмодуле:

```text
src/parsers/aggregators/<source>/geography.py
src/parsers/ats/<platform>/geography.py
```

При необходимости нескольких файлов используется пакет `geography/` вместо одного файла. Выбор фиксируется в плане и не требует перестройки остальных источников.

Этот подмодуль содержит получение и разбор географического справочника, сопоставление общего ввода, правила кеша, оценку точности и подготовку географических параметров запросов. `parser.py` вызывает этот механизм при подготовке поиска и сохраняет необходимые условия в запросах следующих страниц.

Общие модели и низкоуровневый транспорт могут оставаться общими. В общий движок, фронт, сервис брифа и общий географический справочник нельзя добавлять ветвления по названию источника или его географические ID.

HTTP-запросы к справочникам и поиску выполняются через штатный транспорт приложения с его лимитами, повторами и диагностикой. Если источнику нужен POST для получения справочника, а текущая подготовка допускает только GET, необходимое изменение общего интерфейса описывается и согласовывается в плане; отдельный скрытый HTTP-клиент внутри конвертера не создаётся.

## 6. География как явно объявленная возможность источника

Каждый адаптер явно объявляет возможности географии поискового запроса, включая отсутствие поддержки. Это объявление не выводится из наличия поля географии в вакансии и не заменяется возможностями постфильтра.

Объявление должно позволять определить:

- поддержку страны, города и нескольких альтернативных мест;
- смысл ограничения: административное место, офис, группа, радиус;
- нативное объединение через «ИЛИ» либо необходимость отдельных запросов;
- зависимость от версии сайта, конкретной доски и её доступных полей;
- необходимость разрешения места через справочник;
- ограничения географии удалённой работы, если она включена в задачу;
- источник без подходящего нативного ограничения.

Общие возможности платформы уточняются для конкретной доски и выбранного места. До завершения динамической подготовки нельзя объявлять точное применение условия, которого фактический запрос не выражает.

Текущие точки интеграции — `SourceAdapter`, `SourceCapabilities`, `SearchPlan` в `src/parsers/interfaces.py`, `SourceService` в `src/services/sources.py` и ответ API в `src/schemas/sources.py`. Их текущие поля `geography`, `query_parameters`, `native_filters` не следует считать уже готовой моделью требуемой точности; изменения контракта нужно явно описать в плане.

Объявленные возможности должны совпадать с подготовленным планом и фактически отправленными запросами. `native` нельзя выставлять только потому, что адаптер умеет принять вручную заданный параметр или источник печатает выбранную метку.

## 7. Сборка запросов и прохождение через движок

- Несколько мест пользователя имеют смысл альтернатив через «ИЛИ». Если источник не умеет выразить их в одном запросе, подготавливаются отдельные ветви с последующим штатным объединением результатов движком.
- У каждой ветви сохраняются её исходное место и собственные условия. Нельзя превратить пары «страна + город» в произвольные сочетания стран и городов или объединить отличающиеся условия удалёнки.
- География сохраняется на всех страницах, при повторах и допустимых перенаправлениях. Проверяется URL, метод и содержимое JSON/form-тела, а не только первая страница.
- Ошибка одной ветви не подменяется пустой выдачей и не должна незаметно уничтожать остальные ветви.
- Лимиты, доступные страницы и достижение бюджета отражаются явно. Ограниченный сбор нельзя назвать полным покрытием источника или страны.
- Дополнительные режимы движка, способные ослаблять условия, например `second_chance`, включаются в план и тесты. Они не должны молча снимать географию вопреки согласованной семантике.

Для проверки используются существующие `SearchEngine` из `src/engine`, `SourceRun` из `src/engine/source_run.py` и `Network` из `src/network/client.py`. Адаптер не создаёт параллельный поисковый движок для обхода ограничений основного.

## 8. Тест-кейсы до начала реализации

До одобрения плана ассистент составляет применимую к источнику матрицу. Для каждого случая записываются компания, вход брифа, ожидаемое соответствие и параметры, ожидаемая точность, способ сравнения и критерий успеха. Ожидания получают из исследования ресурса, а не из результата будущего конвертера.

| Группа | Обязательные случаи |
|---|---|
| Охват места | Вся страна; выбранный город с регионом; несколько мест одной страны и разных стран |
| Максимум формы | Текущее максимально допустимое число мест; сочетание страны целиком и городов, если это разрешает форма |
| Языки и идентичность | RU/EN или другие доступные алиасы одного выбранного места; нелатинские символы и диакритика; одноимённые города с разными регионами |
| Разный охват | Точный город; более широкая группа/офис/радиус; источник или доска без нужного фильтра |
| Отсутствие соответствия | Допустимое место фронта, которого нет в справочнике источника; неоднозначные варианты; отсутствие нативного поля страны или города |
| Состояние справочника | Холодный кеш; повторное использование; обновление; исчезнувшее или устаревшее значение |
| Пагинация и транспорт | Минимум две страницы там, где они есть; сохранение географии в GET, JSON или form; поддержанные перенаправления и повторные запросы |
| Взаимодействие условий | Несколько поисковых фраз; разные условия у мест; применимые режимы движка; многолокационные вакансии |
| Ошибки ресурса | Игнорирование или сброс фильтра, ошибка справочника, блокировка, недоступность, превышение бюджета |
| Нулевой результат | Реально существующее допустимое место с нулевой выдачей, отличимое от ошибки и неразрешённого места |

Если случай невозможен для исследованного варианта ресурса, указывается конкретная причина и альтернативная проверка соответствующего ограничения. Нельзя удалить неудобный случай без объяснения и назвать матрицу полной.

## 9. Обязательная живая приёмка

### Требуемый уровень запуска

Приёмочный прогон использует пользовательский бриф в общем формате, его штатную валидацию и сохранение, запуск через сервис приложения, реальный `SearchEngine`, реальный адаптер и реальную сеть до источника. Нельзя передавать в бриф готовые ID источника, заранее собранный `SearchRequest` или обходить конвертер ручным заполнением `Board.native_filters`.

Предпочтительный вход — API создания брифа и запуска поиска. Допустим эквивалентный проверочный запуск через те же `BriefService` и `RunService`, если план показывает, что выполняются те же проверки, нормализация, сохранение и исполнение движка. Прямой вызов `prepare()`/`build()` и одиночный `curl` являются исследованием, но не заменяют такой прогон.

Сейчас обычный реестр в `src/parsers/registry.py` подключает HH и Getmatch. Для ATS план обязан описать регистрацию реальных адаптеров выбранных компаний в изолированной конфигурации того же приложения и движка. Наличие готового парсера в библиотеке не доказывает, что пользовательский запуск достигнет его. Отдельный упрощённый исполнитель для приёмки не допускается.

Используется изолированная тестовая база и явно заданная конфигурация. Нельзя изменять пользовательские брифы, историю и настройки ради приёмки. Сохранённые результаты и сетевой кеш не заменяют свежие ответы источника: доказательства должны показывать реальные обращения, а не только завершение повторного запуска.

### Что должно быть доказано

1. Сохранённый бриф содержит общий выбор места, а не вручную подставленную географию сайта.
2. Конвертер автоматически получает данные и разрешает место либо выдаёт согласованный явный результат невозможности перевода.
3. Объявленные возможности соответствуют варианту доски и фактическому результату подготовки.
4. Движок действительно отправляет ожидаемые параметры, включая следующие страницы.
5. Ответ источника соответствует установленному смыслу запроса или источник сообщает установленное ограничение.
6. Для положительного геопоиска есть различающий контроль, а не только HTTP 200 или одна пустая выдача.
7. Доказательство относится к исходным ответам поиска до постфильтрации. Сокращение итоговой таблицы локальным отбором не считается подтверждением серверного фильтра.
8. Для ATS выполнен живой прогон минимум по 10 компаниям и закрыты различия из согласованной матрицы.

Моки, `MockTransport`, сохранённые HTTP-ответы и тесты только преобразования объектов не подходят как основание приёмки. Они могут дополнительно защищать код от регрессий, но не заменяют реальный поиск через движок. При недоступности источника проверка получает статус блокировки или неполного выполнения; работу нельзя объявлять проверенной целиком.

### Доказательства и воспроизводимость

Для каждого случая сохраняются:

- дата и время с часовым поясом, компания, URL доски и вариант интерфейса;
- исходный и нормализованный бриф, конфигурация и команда запуска;
- идентификатор запуска, объявленные возможности и результат подготовки по каждому месту;
- происхождение выбранных значений справочника;
- фактически отправленные URL, методы и тела запросов, включая пагинацию;
- статусы и необходимые фрагменты исходных ответов, ID вакансий и итог сравнения;
- ожидаемый результат, фактический результат и статус случая;
- достигнутые лимиты, блокировки, расхождения и их влияние на вывод.

Доказательства не содержат ключей, cookies, пользовательских токенов и иных секретов. В плане заранее задаются пути отчёта, снимков и воспроизводимого сценария. Для изменяемых сайтов сохраняются необходимые снимки: одна дата без ответа не позволяет проверить исторический результат.

Не требуется закреплять вечное число вакансий. Проверяются параметры, семантика, идентичность мест, отношения контрольных выдач и наблюдаемый результат на дату прогона.

## 10. Критерии готовности и передача следующему ассистенту

Работа завершена, когда одновременно выполнены условия:

- пользователь одобрил показанный план источника и существенные последующие изменения;
- реальные возможности повторно проверены, а для ATS исследованы и прогнаны минимум 10 компаний;
- любой допустимый ввод фронта получает определённый результат без ручных географических маппингов;
- специфичная логика расположена в подмодуле источника, а его возможности объявлены явно;
- запросы и пагинация сохраняют согласованный смысл; неподдерживаемые условия не скрываются;
- тест-кейсы были определены до реализации, живой прогон через штатный движок выполнен и доказательства сохранены;
- необходимые проверки качества проекта прошли, область изменений и ограничения задокументированы;
- непроверенные варианты и временные блокировки явно отделены от подтверждённой функциональности.

При подтверждённом отсутствии нативного геопоиска результатом согласованной доработки могут быть явное объявление отсутствия поддержки и корректная диагностика. Это завершение такой ограниченной задачи, а не реализация точного поиска по городу.

Для текущего проекта базовые проверки кода выполняются из корня репозитория:

```sh
uv run ruff check src scripts tests benchmarks
uv run mypy
uv run pytest -q
```

Они дополняют обязательный живой прогон. Точную команду живого сценария для конкретного источника ассистент добавляет в его план и отчёт; универсальной команды, уже проверяющей все ATS через пользовательский вход, этот документ не заявляет.

### Содержание плана, передаваемого пользователю на ревью

1. Источник, варианты интерфейса и конкретная доработка.
2. Проверенная текущая функциональность и отличия от предыдущих описаний.
3. Для ATS — таблица минимум 10 компаний и объяснение покрытия различий.
