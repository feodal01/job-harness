# План: факты вакансии в словаре брифа

Дата: 03.11.2026. Статус: этап 1 (контракт) согласован 03.11.2026; этап 2 (каркас) и этап 3 (Getmatch) согласованы и выполнены 03.11.2026; этап 4 (постфильтр) — план и решения согласованы 04.11.2026 (§11).
Связанные документы: [требования к географии источника](source-geography-implementation-requirements.md),
[план Getmatch](getmatch-geography-plan.md), [проверка relocate/sa](experiments/getmatch-salary-relocation-2026-11-03/report.md).

## 1. Принцип

Бриф задаёт условия в общем словаре: страна ISO, `geoname_id`, формат работы, релокация, занятость,
зарплата (сумма, валюта ISO, период), опыт в годах, дата. Поиск переводит этот словарь в параметры
источника. **Нормализация вакансии делает обратный перевод:** из данных и справочников источника
она заполняет факты вакансии в том же словаре и с теми же типами. Собственный формат не придумывается.
Постфильтр сравнивает поле с полем: `geoname_id` с `geoname_id`, ISO с ISO.

Правила те же, что для поиска (§4 требований):

- значения берутся из справочников источника (иерархия мест, коды, словари интерфейса)
  или из общих справочников с известным происхождением (CLDR, GeoNames);
- ручные таблицы «подпись → код» запрещены; исключения согласуются явно, как для зон Getmatch;
- «неизвестно» (`None`) допустимо, догадка — нет; неоднозначность остаётся неизвестностью;
- у факта есть происхождение: структурированное поле источника или текст; разбор текста помечается.

## 3. Контракт

### Место вакансии — `VacancyPlace` (заменяет `WorkLocation`)

Зеркало `SearchPlace` плюс формат и релокация этого места:

| Поле | Тип | Смысл |
|---|---|---|
| `scope` | `city` / `region` / `country` / `world` / `group` | что известно о месте |
| `country` | ISO из полного каталога (`country_codes()`) или `None` | |
| `geoname_id` | `int` или `None` | только для `city`, только при однозначном сопоставлении |
| `region` | название региона GeoNames или `None` | для `city` и `region` |
| `format` | `WorkFormat` или `None` | формат работы в этом месте |
| `relocation_support` | `bool` или `None` | помощь с переездом в это место |
| `excluded` | `bool` | место явно исключено («кроме РФ») |
| `label` | строка источника | для показа и диагностики, не для сравнения |
| `evidence` | `Evidence` | происхождение |

`group` — именованная группа без известного состава («Европа», «EU»): страна неизвестна.
`world` заменяет флаг `worldwide`. Строка `city` удаляется после перевода всех источников.

### Остальные факты

| Условие брифа | Факт вакансии | Изменение |
|---|---|---|
| `minimum_work_format` | `places[].format` | `work_formats` удаляется; формат без места — место с `country=None` |
| `relocation_support` | `places[].relocation_support` | новое |
| `salary` (`SalaryFilter`) | `salary: VacancySalary` — `from`, `to`, `currency` ISO 4217, `period` того же типа, `gross`, `hidden` | вместо dict + `salary_hidden` |
| `employment` | `employment: list[Employment]` | без изменений типа |
| `experience_years` | `min_experience`, `min_experience_exclusive` | без изменений |
| `published_after` | `published_at` | без изменений |
| `excluded_companies` / `excluded_text` | `company.name`, тексты | без изменений |

`Evidence`: `enricher` (кто установил факт, например `getmatch`, `text.relocation`), `method`
(`structured` — поле источника, `text` — разбор текста, `inferred` — вывод модели или эвристики),
`field` (путь в `source_data` или поле текста), `raw` (сырое значение).
Для фактов уровня вакансии — `evidence: dict[str, list[Evidence]]` по имени факта.

### Расширяемость: несколько обогатителей и новые типы фактов

Факты заполняет не один нормализатор, а цепочка **обогатителей** (`Enricher`). Сначала идёт нормализатор
источника (структурированные данные), затем общие обогатители, которые не зависят от источника:
сейчас — разбор текста (релокация, «удалёнка по миру», исключения стран), позже — любые новые
инструменты, например извлечение параметров моделью. Новый инструмент добавляется как ещё
один обогатитель, без правки нормализаторов источников и постфильтра.

| Правило | Содержание |
|---|---|
| Интерфейс | `Enricher.id`, `Enricher.facts` (какие факты умеет ставить), `enrich(vacancy) -> list[FactUpdate]` |
| Регистрация | общие обогатители — в реестре; цепочка источника = его нормализатор + общие обогатители |
| Приоритет | `structured` > `text` > `inferred`; более слабый метод не перезаписывает более сильный, а только заполняет `None` |
| Конфликт | разные значения разных обогатителей не затирают друг друга: факт берёт значение по приоритету, конфликт сохраняется в `evidence` и виден в диагностике |
| Новые типы фактов | реестр типов фактов: имя → тип значения (`FACT_TYPES`). Факты условий брифа — обязательная часть реестра; новый инструмент может объявить новый факт (например, уровень английского или стек) без изменения модели вакансии: такие факты лежат в `facts: dict[str, Fact]` и проверяются по типу из реестра |
| Связь с брифом | постфильтр проверяет только факты, для которых есть условие брифа; новый факт становится условием только после отдельного решения (новое поле `SearchFilters`, `FilterName`, проверка) |
| Повторяемость | обогатители детерминированы или кешируют результат по входу; повторная нормализация из `source_data` даёт те же факты при той же версии обогатителя; версия хранится в `evidence` |

Общие обогатители — только для инструментов, не зависящих от источника (например, будущий разбор текста моделью).
Эвристики конкретного источника живут в его нормализаторе.

`location` (подпись источника, например «Москва, Казань») остаётся текстом для показа; постфильтр его не читает.
`grades` не условие брифа — вне задачи.

### Общие помощники (без таблиц) — `src/geography/resolve.py`

- `country(label)` → ISO: точный ISO-код или название из CLDR на любом из 463 языков каталога.
- `city(country, label, region=None)` → `geoname_id` или неоднозначность/ненайдено через `CityLookup`.
- `region(country, label)` → регион GeoNames.

Справочник источника имеет приоритет (HH `countryIsoCode`, иерархия Getmatch, ISO в ATS);
общие помощники — для подписей.

## 4. Размещение кода

```text
src/parsers/aggregators/<source>/enrichment.py   нормализатор источника (structured)
src/parsers/ats/<platform>/enrichment.py         нормализатор платформы ATS
src/enrichment/                                  контракт Enricher, реестр фактов, цепочка и слияние
```

`SourceAdapter.enrich: Callable[[Vacancy], Vacancy]` строит факты из `source_data` и полей вакансии.
Движок (`recorder`, `reuse`, `pool`) вызывает обогащение по id источника вместо
`normalize_stored_vacancy(vacancy, source)`. Для сохранённых вакансий источника,
которого нет в текущем реестре, обогащение берётся из реестра нормализаторов по id платформы.
`geography.py` источника переводит в обе стороны: бриф → параметры поиска, данные вакансии → места.

## 5. Порядок работ

Каждый этап — отдельный план и одобрение; источник считается переведённым после живой проверки.

| Этап | Содержание | Поведение |
|---|---|---|
| 1 | Этот контракт | — |
| 2 | Каркас: `VacancyPlace`, `VacancySalary`, `Evidence`, реестр фактов, `Enricher` и цепочка, `resolve.py`, `SourceAdapter.enrich`; движок вызывает цепочку; текущие ветки Getmatch и HH переносятся в их папки, регэкспы — в общий обогатитель текста, как есть | не меняется (тесты) |
| 3 | Getmatch: места через иерархию и общие помощники, `relocation_company` → `relocation_support`, форматы, зарплата | живая проверка на ленте |
| 4 | Постфильтр читает новые факты; переходная ветка для ещё не переведённых источников | сравнение решений до/после на одном снимке |
| 5 | HH | живая проверка |
| 6…N | ATS по платформам, по одной; заодно удаляется их доля `ats/normalization.py` | живая проверка платформы |
| N+1 | Удаление `normalization.py`, `ats/normalization.py`, `COUNTRIES`/`COUNTRY_EN`, строк `city`, `work_formats`, переходной ветки постфильтра; ответ API и UI на новые поля | тесты, живой прогон |

## 6. Приёмка источника

На свежем живом снимке источника:

- доля мест с `geoname_id` / ISO, групп, неоднозначных и неизвестных — с примерами каждого вида;
- ни одного значения без происхождения; выборочная ручная сверка с сайтом;
- решения постфильтра до и после на одном снимке, каждое изменение объяснено;
- повторная нормализация сохранённых вакансий даёт те же факты.

## 7. Решения и открытые вопросы

Решено 03.11.2026:

1. Имя `VacancyPlace` (зеркало `SearchPlace`) вместо `WorkLocation`.
2. `scope=region`: подпись региона разрешается через `region_names` GeoNames (189 813 названий,
   430 языков) в `region_id`; город брифа совпадает с местом, если его `region_id` равен региону места.
   Без регэкспов и списков; ненайденная подпись — «неизвестно».
3. Группы мест — в общем справочнике географии, из Unicode CLDR: `territoryContainment`
   (регионы ООН M49, `EU`, `EZ`) и локализованные названия групп. Требует расширения
   `scripts/build_geography.py` (сейчас из CLDR берутся только названия стран) и проверки данных
   при сборке. Группы вне CLDR (СНГ, EMEA, APAC, DACH, MENA) — «неизвестно» либо согласованное
   исключение с источником состава, по факту появления в данных.

4. Ответ API (`results`, `vacancies`, MCP `get_results`/`list_vacancies`) меняет форму на этапе N+1:
   `locations` → `places`, удаляются `work_formats` и `salary_hidden`, `salary` типизируется.
   Внешних клиентов нет: веб-интерфейс, MCP и плагин обновляются в том же этапе, версия плагина поднимается.
5. Существующие регэкспы разбора текста (RU/EN) — эвристика HH: переносятся как есть внутрь `hh/enrichment.py`;
   останутся ли они, решается на этапе HH. Новых регэкспов не добавляется; другие языки — через будущий обогатитель текста.

## 8. Этап 2: каркас без изменения поведения (выполнен 03.11.2026)

Цель — новая структура, в которую дальше переезжают источники. Решения постфильтра не меняются.

### Что делается

1. **Модель** (`src/models/filters.py`, `src/models/vacancy.py`):
   - `WorkLocation` переименовывается в `VacancyPlace`; на переходный период остаётся псевдоним
     `WorkLocation = VacancyPlace` (удаляется на этапе N+1);
   - у места появляются новые необязательные поля: `scope`, `geoname_id`, `region`, `relocation_support`,
     `label`, `evidence`; старые `city`, `worldwide` остаются до этапа N+1. Поле вакансии пока называется `locations`;
   - `Evidence` (`enricher`, `method`, `field`, `raw`, `version`) и `Vacancy.facts: dict[str, Fact]`
     для фактов вне условий брифа. Пока их никто не заполняет.
   - Типизированная зарплата (`VacancySalary`) — отдельный этап после мест: она затрагивает все
     23 парсера и постфильтр.
2. **`src/enrichment/`**:
   - `contract.py` — `Enricher` (`id`, `version`, `facts`, `enrich(vacancy) -> list[FactUpdate]`), `FactUpdate`, порядок методов;
   - `registry.py` — реестр типов фактов (`FACT_TYPES`) и реестр обогатителей по id источника;
     для ATS id вида `ats:<платформа>:<доска>` ищется по платформе; неизвестный источник — только общие обогатители;
   - `chain.py` — запуск цепочки и слияние: `structured` > `text` > `inferred`, слабый метод только
     заполняет пустое, конфликт сохраняется в `evidence`;
   - `text/` — перенос без изменений `WORLDWIDE`, `_worldwide`, `_excluded_countries` из `normalization.py`.
3. **Нормализаторы источников**: ветка Getmatch и `getmatch_locations` → `getmatch/enrichment.py`;
   ветка HH вместе с её регэкспами → `hh/enrichment.py`. Код переносится как есть.
4. **Движок**: `recorder`, `reuse`, `pool` и парсеры Getmatch/HH вызывают `enrich(vacancy, source_id)`
   вместо `normalize_stored_vacancy`. Реестр обогатителей не зависит от включённых источников:
   сохранённые вакансии отключённого источника обогащаются так же.
5. **`src/geography/resolve.py`**: `country(label)` (ISO-код или название CLDR на любом языке каталога),
   `city(country, label, region)`, `region(country, label)` через GeoNames. Используются с этапа 3.
6. В `normalization.py` остаются только `FORMATS` и `COUNTRY_EN` (ими пользуются ATS) — до их этапов.

### Проверка

- Весь набор тестов без изменения ожиданий.
- Эквивалентность: старая `normalize_stored_vacancy` и новая цепочка дают одинаковые вакансии на всех
  фикстурах HH/Getmatch и на живом снимке Getmatch от 03.11 (962 вакансии); тест удаляется вместе со старым кодом.
- Новые тесты: слияние по приоритету и конфликт, поиск обогатителя для `ats:greenhouse:<доска>`,
  обогащение вакансии отключённого источника, `resolve.py` на подписях из снимка Getmatch
  (RU/EN/другие языки, неоднозначность, не найдено).
- Живой прогон не нужен: запросы и решения не меняются, это подтверждает эквивалентность.

### Результат этапа 2

## 9. Этап 3: Getmatch (выполнен 03.11.2026)

### Исходные данные Getmatch

Каждая вакансия ленты содержит `location_requirements` — структурированные места:
`location_id` (`kazan__tatarstan__russia`), `ancestors` (`kazan`, `tatarstan__russia`, `russia`, `_cu-europe`,
`_cu-emea`, `_cu-world`), подписи `city`/`country` на русском, `format` и `exclude`.
Значения `format` в ленте 03.11: `office`, `hybrid`, `remote`, `relocation_company`; словарь интерфейса Getmatch
называет `relocation_company` «релокация за счёт компании» и знает также `relocation_candidate` («за счёт кандидата»).
Группы Getmatch: `_cu-world`, `_cu-europe`, `_cu-emea`, `_cu-european-union`.
Снимок 03.11 (93 уникальные подписи): 47 городов и 26 стран разрешаются текущими справочниками;
6 — группы; 10 — подписи стран вне собранного каталога («США», «Turkey», «Словацкая Республика»…);
4 — регион или мусор («Московская область», `unknown`, строка из шести городов).

### Что делается

1. **Каталог CLDR** (`scripts/build_geography.py`, `src/geography/data/countries.json.gz`):
   - альтернативные названия стран из тех же `territories.json` (`US-alt-short` «США», `TR-alt-variant` «Turkey»…);
   - группы: названия кодов M49 и группировок (`001` «весь мир», `150` «Европа», `EU`…) на всех языках каталога
     и их состав из `cldr-core/supplemental/territoryContainment.json` (проверено: CLDR 49, `EU` — 27 стран);
   - источник — релиз `cldr-json` 49; URL, версия и SHA-256 — в `metadata`; сборщик получает путь к `cldr-core`.
   - `resolve.country` ищет и по альтернативным названиям; новый `resolve.group(label)` → код группы CLDR.
2. **Контракт места**: в `VacancyPlace` добавляется `group: str | None` — код группы CLDR для `scope=group`
   (`150`, `EU`); группа без кода CLDR (`_cu-emea`) — `scope=group`, `group=None`, состав неизвестен.
3. **Обогатитель Getmatch — по шагам на тип данных.** Место — один факт (география + формат + релокация),
   поэтому шаги не отдельные звенья цепочки, а шаги одного обогатителя, как `StagedSearch` у поиска.
   Базовый `StagedEnricher` (`src/enrichment/`) для каждой сырой записи вызывает независимые
   `_place_geography`, `_place_format`, `_place_relocation`; связывает их только `_combine` → `VacancyPlace`.

   ```text
   src/parsers/aggregators/getmatch/enrichment/
       __init__.py    GetmatchEnricher: записи location_requirements → места
       geography.py   весь мир / группа / страна / регион / город (ISO, geoname_id, group)
       formats.py     office/hybrid/remote → формат; relocation_* → None
       relocation.py  relocation_company → True, relocation_candidate → False, иначе None
   ```

   | Запись Getmatch | Место |
   |---|---|
   | `kazan__tatarstan__russia`, «Казань», «Россия», `hybrid` | город, `RU`, `geoname_id` 551487, `hybrid` |
   | `russia`, «Россия», `remote` | страна `RU`, `remote_country` |
   | `_cu-world`, «Весь мир», `remote` | `world`, `remote_worldwide` (связь в `_combine`) |
   | `_cu-europe`, «Европа», `remote` | `group`, `group=150`, `remote_country` |
   | `cyprus`, «Кипр», `relocation_company` | страна `CY`, `format=None`, `relocation_support=True` |
   | `mo__russia`, «Московская область» | `region` 524925, `RU` |
   | `country: "unknown"`, «Екатеринбург» | город без страны и `geoname_id`, подпись сохраняется |

   Страна — по подписи через `resolve.country`, затем по slug страны из `ancestors`; город — `resolve.city`,
   неоднозначность или не найдено → `geoname_id=None`. Формат места релокации — `None`: в словаре
   интерфейса Getmatch «релокация» — отдельный вариант формата наравне с «офис/гибрид» и «удаленка»,
   и страница вакансии только с релокацией (32642) показывает лишь «📍 Кипр» и «Помощь с переездом».
   У каждого места `label` и `evidence` (`structured`, `location_requirements[i]`, `raw=location_id`).
   Переходные `city`/`worldwide` заполняются как раньше. `work_formats` — из форматов мест.
4. Часть `FORMATS` Getmatch переезжает в `getmatch/enrichment.py` (свой словарь кодов, включая `relocation_*`);
   `COUNTRIES` в Getmatch больше не используется.

Постфильтр не меняется (этап 4), но его решения по Getmatch могут измениться: распознаётся больше стран
(раньше — 32), а места релокации больше не выбрасываются.

## 10. Один справочник географии (выполнен 03.11.2026)

Решение пользователя 03.11.2026: вариант B — один объект справочника для брифа, API и обогащения;
у каждого источника справочных данных **одна версия** («не плодить версий справочника, одна правда»).

### Что сейчас нарушает «одну правду»

| Что | Версия | Кто использует |
|---|---|---|
| `countries.json.gz` (названия стран) | CLDR старше 49 | каталог стран в API/UI, проверка брифа, `resolve.country` |
| `territories.json.gz` | CLDR 49 | `resolve` (альтернативные названия, группы) |
| `cities.sqlite` | GeoNames `cities15000`, 243 страны | `CityLookup`: подсказки, проверка брифа, `resolve`, постфильтр, HH |
| `cities.json.gz` + `metadata.json` | GeoNames `cities500`, 32 страны | `directory.py`: `match_city` (постфильтр, места брифа без `geoname_id`), `uniquely_identifies_city` (HH) |
| `COUNTRIES` (32 страны, вручную) | — | HH-поиск и обогатитель HH, `ats/normalization.py`, `directory.py` |
| Доступ | прямые импорты модулей | `resolve` (Getmatch), `default_lookup()` (HH, постфильтр), `country_codes()` (валидатор брифа) |

### Что делается

1. **CLDR одной версии (49).** Новый сборщик `scripts/build_cldr.py` (вместо `build_territories.py`) собирает один
   файл `cldr.json.gz`: названия стран, альтернативные названия, группы и их состав, версия и SHA-256 в метаданных.
   `countries.json.gz` и `territories.json.gz` удаляются. `build_geography.py` собирает только `cities.sqlite`;
   CLDR-поля из метаданных SQLite убираются. Последствия: у HM, TF, SH другое английское название (сохранённые брифы
   с ними потребуют пересохранения), подписи стран на части языков меняются, набор языков: +`cop`, −`ht`.
2. **Объект справочника** `GeographyCatalog` (`src/geography/catalog.py`): `CityLookup` + данные CLDR; методы —
   каталог стран, подсказки и проверка города брифа (как сейчас), разбор подписей вакансий (`country`, `group`,
   `group_countries`, `city`, `region`, …; переносятся из `resolve.py`, модуль удаляется).
   Один экземпляр на процесс (`default_catalog()`): `app.py` передаёт его в `GeographyService`, `BriefService`,
   реестр источников и обогащение; валидатор `SearchPlace` (pydantic не принимает зависимости) берёт тот же экземпляр.
3. **Обогащение получает справочник явно.** `build_sources(settings, catalog)`, обогатители создаются с `catalog`;
   движок (`recorder`, `reuse`, `pool`) вызывает обогащение через объект, переданный при старте, а не через импорт.
4. **Старая копия GeoNames и `COUNTRIES`** — вторая версия данных. Удаляются вместе с последними потребителями:
   ветка `match_city` постфильтра — этап 4 (места брифа без `geoname_id` сохранять уже нельзя);
   HH (`uniquely_identifies_city`, `COUNTRIES` в поиске и обогатителе) — этап 5; `ats/normalization.py` — этапы ATS.
   До тех пор они явно помечены в README как устаревшая вторая версия.

### Проверка

Все тесты; Getmatch-обогащение на снимке 03.11 даёт те же факты (кроме названий из новой версии CLDR);
API `/geography/countries` — разница названий перечислена в отчёте; проверка сохранённых брифов.

Решение пользователя: старую копию GeoNames и `COUNTRIES` удалить сразу.

### Результат

- `src/geography/data/`: только `cldr.json.gz` (CLDR 49, `scripts/build_cldr.py`), `cities.sqlite` (GeoNames
  `cities15000`, CLDR-поля из метаданных удалены), `iso3166.json`, `UNICODE-LICENSE.txt`. Удалены `countries.json.gz`,
  `territories.json.gz`, `cities.json.gz`, `metadata.json`; модули `lookup.py`, `countries.py`, `resolve.py`, `directory.py`.
- `GeographyCatalog` (`src/geography/catalog.py`), один экземпляр; `app.py` передаёт его в `BriefService`,
  `GeographyService`, `build_sources` (HH) и `Enrichment`. Валидатор брифа, постфильтр и `ats/normalization.py`
  до своих этапов берут тот же экземпляр через `default_catalog()`.
- Обогащение — объект `Enrichment(catalog)`; его вызывает движок после разбора ленты и карточки (`SourceRun`),
  а также рекордер, переиспользование карточек и пул. Парсеры больше не обогащают сами.
- `COUNTRIES` заменён CLDR: HH сопоставляет свой список стран через `catalog.country`, обогатитель HH строит
  исключения стран по названиям CLDR (все 249 стран, ru/en), ATS — `catalog.country`.
- Изменения поведения: города брифа сравниваются только по `geoname_id` (брифы без него запускать уже нельзя);
  английские названия HM, TF, SH и часть локализованных подписей по CLDR 49; набор локалей +`cop`, −`ht`;
  ATS: «United States of America» не распознаётся (такого названия нет в CLDR; решается на этапах ATS по кодам платформ);
  HH: «Троицк (Москва)» под «Московская область» в HH не сопоставляется с GeoNames (Москва) — консервативно,
  зафиксировано тестом для этапа HH.
- Проверка: 976 тестов в `tests/`, mypy, ruff; Getmatch на снимке 03.11 — те же 1294 места.


## 11. Этап 4: постфильтр по фактам (согласован 04.11.2026)

Цель: постфильтр только сравнивает условия брифа с фактами вакансии в одном словаре. Каждое условие
проверяется в своём модуле, разбора текста в фильтре нет. Решение пользователя 04.11.2026: регэкспы релокации
уходят из фильтра в обогатитель HH.

### Что сейчас

`src/selection/filtering.py` (~330 строк) смешивает в одном файле всё:
- сравнение мест строками (`catalog.matches(geoname_id, place.city)`);
- подстановку форматов всей вакансии (`work_formats`) месту без формата;
- разбор текста описания на релокацию (`_relocation`, около десяти регэкспов на RU/EN);
- проверки зарплаты, опыта, даты и компаний подряд в теле `evaluate`.

Факты Getmatch этапа 3 (`scope`, `geoname_id`, `region`, `group`, `relocation_support`) фильтр не читает.
Справочник берётся через `default_catalog()`.

### Структура после этапа

```text
src/selection/
    filtering.py            evaluate(): применяет проверки из CHECKS, сводит итог (accepted/maybe/rejected)
    checks/
        __init__.py         Check: name, kind (hard/soft), applies(filters), check(vacancy, ctx) -> FilterCheck
                            Context: catalog, complete, queries, unsupported; CHECKS — список проверок по порядку
        profile.py          профиль: название и навыки (match_profile, без изменений)
        places/             условия мест брифа: география + формат + релокация одного варианта
            __init__.py     варианты «место вакансии × место брифа», выбор лучшего варианта целиком;
                            выдаёт три FilterCheck: locations, minimum_work_format, relocation_support
            geography.py    место брифа против места вакансии по scope (таблица ниже) и исключения
            format.py       формат варианта против минимума брифа (FORMAT_RANK)
            relocation.py   relocation_support варианта против требования брифа
            legacy.py       география без scope (HH, ATS): сравнение строкой города, формат из work_formats;
                            перенос текущего кода как есть, удаляется на этапе N+1
        employment.py
        experience.py
        salary.py           правило §3.5 спецификации без изменений (VacancySalary — отдельный этап)
        published.py
        companies.py        исключённые компании
        excluded_text.py    поиск слов пользователя в тексте: это его условие, а не наш словарь
```

Правила:
- одно условие брифа — один модуль;
- проверка читает только поля вакансии и брифа: фильтр ничего не разбирает и не угадывает;
- `places/` повторяет шаги `StagedEnricher` (география, формат, релокация).

Перечень условий в `CHECKS` совпадает с `FILTER_NAMES`: это проверяется тестом, как сейчас `test_filter_names.py`.

### Что делается

1. **Переписать постфильтр по структуре выше.** Поведение условий, кроме мест и релокации, не меняется:
   код переносится из `evaluate` в модули без изменения логики. Причины проверок те же или точнее.

2. **Релокация — только из фактов.** `checks/places/relocation.py` читает `relocation_support` того места,
   которое выбрано в варианте. `None` → «неизвестно». `_relocation` и все регэкспы удаляются из фильтра.

3. **Регэкспы релокации — в обогатитель HH** (`src/parsers/aggregators/hh/enrichment.py`). Код переносится как есть,
   как «удалёнка по миру» на этапе 2. Это частная эвристика HH для русских и английских формулировок;
   останется ли она, решается на этапе 5. Результат ставится в `relocation_support` неисключённых мест HH.
   Пока нет полного описания (только лента), значение `None`, как сейчас. Тесты на формулировки переезжают
   из `tests/test_filters.py` в тесты обогатителя HH с теми же ожиданиями. Последствие для ATS: релокация
   у них «не проверено», пока платформа не переведена. Раньше регэксп давал «да» или «нет», и «нет» понижало
   вакансию до «может быть».

4. **Выбор ветки географии.** Новая ветка — если у мест вакансии заполнен `scope`. Его ставит `StagedEnricher`,
   сейчас это только Getmatch. Без `scope` работает `legacy.py`: HH и ATS решают по географии и формату так же,
   как сейчас. Признак берётся из данных, а не из списка источников: источник переходит на новую ветку сам,
   когда его обогатитель начинает заполнять `scope`. Ветки внутри одной вакансии не смешиваются.

5. **География (`geography.py`).** Место брифа — страна или город (`country`, `geoname_id`). Регион города брифа
   берётся из справочника (`catalog.city_region(geoname_id)`), а не из строки брифа. Названия регионов уникальны
   внутри страны (проверено на `cities.sqlite`), поэтому пара (страна, регион) однозначна. Сравниваются только
   идентификаторы из справочника. Текст в этой проверке не разбирается: подпись региона переводит в имя региона
   GeoNames обогатитель источника (`catalog.region`), поэтому правило одно для любого источника, заполняющего `scope=region`.

   | Место вакансии | Бриф: страна | Бриф: город, удалёнка | Бриф: город, офис/гибрид |
   |---|---|---|---|
   | `world` | да | да | да (формат решает отдельно) |
   | `group` с кодом CLDR | страна в `group_countries` → да, иначе нет | так же | страна в группе → неизвестно, иначе нет |
   | `group` без кода (`_cu-emea`) | неизвестно | неизвестно | неизвестно |
   | `country` | ISO равны → да, иначе нет | так же | другая страна → нет, та же → неизвестно |
   | `region` | по стране | по стране | (страна, регион) равны → да, иначе неизвестно |
   | `city` с `geoname_id` | по стране | по стране | `geoname_id` равны → да, иначе нет |
   | `city` без `geoname_id`, страна известна | по стране | по стране | другая страна → нет, та же → неизвестно |
   | страна неизвестна | неизвестно | неизвестно | неизвестно |

   Если формат места неизвестен, другая страна даёт «неизвестно», а не «нет»: так же работает текущий код,
   потому что место может разрешать удалёнку по миру. Исключённые места (`excluded`) сравниваются по той же
   таблице: совпадение исключает вакансию, «неизвестно» оставляет проверку неизвестной.

6. **Формат (`format.py`).** В новой ветке варианты строятся только из мест: у места без формата формат неизвестен.
   Форматы других мест вакансии к нему не приписываются, `work_formats` не читается (контракт §3).

7. **Getmatch: записи одного места.** Getmatch хранит вакансию как список пар «место + один вариант».
   Пример 36643: `cyprus/relocation_company` и `cyprus/hybrid`. 15 вакансий снимка 03.11 содержат релокацию
   в паре с другим форматом того же `location_id`. Обогатитель Getmatch (версия 3) ставит `relocation_support`
   записи релокации всем записям того же `location_id` в этой вакансии. Если других записей у места нет,
   остаётся место с `format=None`. Объединение идёт только внутри одной вакансии. Отсутствие записи релокации
   остаётся `None`: в словаре Getmatch это необязательная опция, а не отказ.

8. **Справочник явно.** `evaluate(..., catalog)` и `FilterStage(..., catalog)`. Движок (`source_run`, `recorder`,
   `pool`) передаёт `enrichment.catalog`. `default_catalog()` из постфильтра уходит.

9. **Причины проверок мест.** Причина называет решающее место (`label`) и то, по чему шло сравнение
   (`geoname_id`, регион, ISO, группа CLDR).

Не входит: типизированная зарплата, HH целиком (этап 5), ATS, удаление `work_formats`/`city`/`legacy.py`,
ответ API и UI (N+1). `FILTER_FIELDS` (заявленные возможности источника) переезжает в `checks/` без изменений:
у `relocation_support` вместо `description`/`summary` поле `locations`.

### Проверка

- Весь набор тестов. Ожидания меняются только там, где решение меняется по пунктам 3, 5–7; каждое такое изменение перечисляется.
- Эквивалентность: замороженная копия текущего `filtering.py` в `tests/` (удаляется на N+1).
  На фикстурах HH решения совпадают; на фикстурах ATS различия только в релокации (пункт 3).
- Новые тесты: каждая клетка таблицы пункта 5, исключения, группа с кодом и без, регион, отсутствие заимствования
  формата и релокации между местами, записи одного места Getmatch, релокация HH из текста, совпадение `CHECKS` с `FILTER_NAMES`.
- Живая приёмка: свежая лента Getmatch, решения старой копии и нового кода на одном снимке. Брифы: шесть из §9,

  как вопрос перевода брифа в параметры поиска.

### Решения

Решено 04.11.2026: регэкспы релокации — в обогатитель HH (пункт 3); записи одного места Getmatch получают
общую релокацию (пункт 7); формат не заимствуется у других мест (пункт 6).

Решено 04.11.2026: город брифа против места-региона при офисе/гибриде, если регион другой, → «неизвестно» (пункт 5).
Причина: регион источника может не совпадать с регионом GeoNames. В GeoNames Москва — отдельный регион, а в иерархии
Getmatch `moscow__mo__russia` Москва входит в `mo__russia` («Московская область»). Справочника мест Getmatch не
публикует, поэтому состав его региона неизвестен. Подмена региона на город отклонена: это догадка и ручная таблица.
«Неизвестно» не отклоняет вакансию, а в причине проверки названо расхождение. Город с другим `geoname_id` → «нет», как и сейчас.
