# Поисковый движок вакансий: спецификация v2 (черновик)

Статус: черновик от 01.10.2026, собран из требований владельца продукта.
Уточнение границ от 08.10.2026: сайт работодателя сохраняется как ссылка для пользователя.
Поиск контактов, поиск карьерных разделов и загрузка или парсинг их лент в требования не входят.
Заменяет общие принципы [search-query-business-rules.md](search-query-business-rules.md);
конкретные переводы HH/Getmatch оттуда остаются в силе, пока не пересмотрены здесь. Правила зарплаты заменены разделом 3.5.
Пометка **[предложение]** — решение ещё не подтверждено. Пометка **[вопрос]** — см. раздел 14.

## 0. Цель и принципы

Цель продукта — **расширить воронку** кандидата: найти больше подходящих вакансий, чем даёт ручной поиск.

1. Пропустить ценную вакансию хуже, чем показать не совсем подходящую.
2. Основной критерий — соответствие **профилю** брифа (кого ищем). Не подошло по профилю — не показываем.
3. Остальные условия (формат, город, зарплата и т. п.) — повод понизить вакансию в «Может быть подходит», а не скрыть её (second chance).
4. Не делать одну и ту же работу дважды: одна вакансия, профиль работодателя — один запрос, сколько бы поисковых фраз их ни нашли.
5. Соблюдать лимиты каждого источника всегда, для любых типов запросов.
6. Найденные в источниках ссылки на сайты работодателей сохраняются вместе с вакансиями и показываются пользователю.

## 1. Понятия

| Понятие | Смысл |
|---|---|
| Бриф | Кого ищем: профиль + условия. Живёт долго, у него много запусков |
| Запуск (run) | Одна сессия сбора по брифу. Пополняет пул брифа |
| Пул брифа | Единая таблица вакансий брифа: всё, что нашли его запуски, с решением фильтров и статусом пользователя. Запуски её наполняют, пользователь в ней работает |
| Источник | Единица сетевой политики: лимиты, ретраи, классификация ответов. Пример: HH, Getmatch |
| Этап | Тип операции внутри источника: лента, карточка, профиль работодателя |
| Задача | Конкретная операция этапа с ключом дедупликации (например `hh:vacancy:123`) |
| База знаний | Сведения о компаниях, их идентичности в источниках, ссылки на сайты и списки компаний. Общая между запусками и брифами |

## 3. Фильтры

### 3.1 Два класса условий

Решение от 01.10.2026:

| Класс | Что входит | Не прошло → |
|---|---|---|
| Жёсткие | Страна, где ищем; город, если задан; профиль вакансии | Не показываем |
| Мягкие (второй шанс) | Формат, занятость, опыт, зарплата, дата, помощь с релокацией | «Может быть подходит» с явной причиной |

Исключённые компании и исключённые фразы — тоже жёсткие: исключили — значит не показываем.

### 3.2 Итог по вакансии

- **Подходит**: жёсткие условия подтверждены, ни одно мягкое не провалено. Неизвестные мягкие условия показываются меткой «не проверено», но вакансия остаётся здесь: принцип 1.
- **Может быть подходит**: жёсткие условия подтверждены или неизвестны, провалено хотя бы одно мягкое.
- **Скрыто**: провалено жёсткое условие. Доступно только в отладочном виде «все».

Каждое условие даёт `подходит / не подходит / неизвестно` и причину. Неизвестность не превращается в отказ.

### 3.3 Соответствие профилю

Профиль проверяем **всегда сами**, в том числе для источников с текстовым поиском: поисковики агрегаторов
(HH ищет и по описанию) возвращают нерелевантное. Выдача источника по фразе — не доказательство.
Реализована общая проверка по названию и навыкам с ограниченным словарём синонимов. Явно другая профессия скрывается; неоднозначное соответствие остаётся непроверенным.

- Сейчас: по названию (и навыкам, если есть) — совпадение с одной из поисковых фраз без учёта регистра, со словарём синонимов. Сомнительное → «неизвестно», а не отказ.
- To-be: по тексту вакансии; агент/ML по описанию профиля.

### 3.4 География и формат работы

Страны и города для брифа берутся из независимого локального справочника GeoNames,
а не из API HH. Снимок `cities500` содержит 112 357 населённых пунктов в текущих 32 странах;
это не все поселения. Название города и регион не содержат ID источников.
Перевод выбранного места в нативные параметры выполняет адаптер при подготовке поиска.
Неподдерживаемое или неоднозначное место даёт явную ошибку соответствующего источника.

Четыре общих формата, от самого привязанного к месту к самому свободному:

**офис < гибрид < удалёнка по стране < удалёнка по миру**

Пользователь задаёт:
- **Места** (жёсткое условие): список «страна + необязательный город».
- **Форматы** (мягкое условие): любые из четырёх; пусто = любые. Заменяет `work_formats` + `remote_from`.

Правила интерпретации вакансии:
- Удалёнка **по миру** — только если это явно указано (структурированное поле источника или текст: «из любой точки мира», «worldwide», «anywhere»). Иначе удалёнка — **по стране** вакансии.
  Отдельного фильтра «удалёнка по миру» у источников обычно нет: у HH есть только «удалённо», поэтому удалёнка по миру на HH распознаётся только по описанию. Getmatch отмечает её в типовом поле (`location_id=_cu-world`).
- Гибрид всегда привязан к городу вакансии: часть времени в офисе, совмещать его с работой из другого города нельзя.

Проверка мест (жёсткая): чем свободнее формат, тем слабее привязка к месту.
| Формат вакансии | Проходит «места», если |
|---|---|
| Офис / гибрид | Город вакансии = заданному городу; если город не задан — страна вакансии входит в «места» |
| Удалёнка по стране | Страна вакансии входит в «места»; заданный город не важен |
| Удалёнка по миру | Всегда, кроме случая, когда вакансия явно исключает страну из «мест» |

Пример: поиск «Россия, Томск». Подходят офис и гибрид в Томске, удалёнка по России, удалёнка по миру.
Офис в Москве скрыт.

Если у вакансии несколько вариантов (например, офис в Москве или удалёнка по России), она проходит, когда проходит хотя бы один вариант. Формат-условие проверяется по тому же варианту.

Порядок форматов действует и для мягкого условия формата (решение 01.10.2026): более свободный формат
всегда подходит тому, кто готов к менее свободному. Выбор «гибрид» принимает гибрид, удалёнку по стране
и удалёнку по миру; «Может быть подходит» получают только более привязанные форматы (офис).
Поэтому в интерфейсе достаточно одного выбора: **«не менее свободный формат, чем…»**. Пусто — любой.
При выключенном «Втором шансе» источнику передаются все форматы не ниже выбранного (HH: `HYBRID` + `REMOTE`).

Названия форматов у каждого источника свои (`ON_SITE`, «Гибрид», `hybrid`...); адаптер обязан перевести их
в общие значения. Если у источника нет такого фильтра, но формат есть в ленте/карточке в стандартном месте,
**источник считается поддерживающим условие** (локальная проверка).

### 3.5 Прочие условия

Занятость, опыт, дата публикации — правила из [search-query-business-rules.md §5](search-query-business-rules.md).

**Зарплата** (решение 02.10.2026). Условие необязательное; пользователь задаёт «от X» (сумма, валюта, период).
Сравнивается с тем, что указано в вакансии; вилка «допускает» X, если её верхняя граница не меньше X:

| Зарплата в вакансии | Итог по условию |
|---|---|
| Не указана | Подходит (не повод понижать) |
| «от A» | A ≥ X → подходит; A < X → второй шанс |
| «от A до B» | B ≥ X → подходит; B < X → второй шанс |
| «до B» (редко) | B ≥ X → подходит; B < X → второй шанс [предложение] |
| Другая валюта или период | Не сравнивается без пересчёта → «не проверено», остаётся в «Подходит» |
| Налоги отличаются («на руки» / «до вычета») | Не пересчитываются; сравнивается сумма как есть [предложение] |
| Условие не задано | Зарплата не фильтр, все вакансии проходят |

Строгий режим «нижняя граница не меньше X» (`strict_minimum`) и условие «только с опубликованной зарплатой»
(`salary_published`) убираются: пользователь задаёт только «от X», а вакансия без зарплаты — первый шанс.
Нативно (при выключенном «Втором шансе») передаётся только фильтр, который не отрезает вакансии без зарплаты
и вилки с B ≥ X. HH `only_with_salary` / `label=with_salary` не используются никогда: вакансия без зарплаты — первый шанс.
HH `salary` и Getmatch `sa` — только после проверки этого свойства на живой выдаче.

**Грейд не фильтруется** (решение 02.10.2026). Грейды разные у разных компаний, нативный фильтр есть у немногих
источников, распознавание по названию ненадёжно. Условие убирается из брифа целиком; вернуть его можно позже
вместе с умным фильтром (агент/ML).

Помощь с релокацией — по тексту карточки. Правила распознают в том числе «Помощь с релокацией», «Релокационный пакет», «Без помощи с переездом»; неоднозначные и противоречивые формулировки остаются непроверенными.
To-be: сложные условия (релокация, удалёнка по миру по тексту, грейд, если вернём) проверяет агент или ML; сейчас — правила, закрывающие основные случаи.

### 3.6 Списки компаний (to-be)

Именованные списки компаний в общей базе знаний, например «госсектор, Россия». Список составляется один раз
и переиспользуется: бриф может исключать компании по списку («не госсектор») или искать только в нём.
Компания в списке — запись базы знаний со всеми её идентичностями в источниках, поэтому список работает
одинаково для HH и Getmatch. Исключение по списку — жёсткое условие, как исключённые компании.

## 4. Перевод условий в фильтры источника

Для каждого условия адаптер объявляет способ применения:

| Способ | Смысл |
|---|---|
| `native` | Передаётся источнику; выдача — надмножество подходящих |
| `local` | Проверяется по данным ленты/карточки |
| `none` | Ни фильтра, ни данных. Условие **пропускается** (не блокирует запуск), но в плане и интерфейсе видно «в этом источнике не проверяется» |

Правила:
1. Нативный фильтр применяется, только если он не может отрезать подходящую вакансию.
2. Жёсткие условия (страна, город) и текст профиля передаются источнику всегда, когда есть безопасный перевод.
   Одно место может потребовать **нескольких нативных запросов**, если одним запросом его не выразить: объединение
   их выдач должно покрывать все вакансии, проходящие «места» (3.4). Пересечения убирает дедупликация (5.4).
   Пример HH, «Россия, Томск»: запрос `area=Томск` (офис, гибрид и всё, что опубликовано в Томске) и запрос
   `area=Россия` + `work_format=REMOTE` (удалёнка по России, опубликованная в любом городе). Если формат-условие
   передаётся нативно и исключает офис и гибрид, первый запрос не нужен.
3. Мягкие условия зависят от настройки сервиса **«Второй шанс»** (`second_chance`):

   | Значение | Мягкие условия источнику | Результат |
   |---|---|---|
   | вкл | Не передаются | Шире выдача и «Может быть подходит», больше запросов |
   | выкл | Передаются все, у которых есть нативный фильтр | Меньше запросов; «Может быть подходит» получает только то, что источник не отфильтровал сам |

   В обоих режимах локальная проверка та же. По умолчанию **выключен**.
   Один запуск = фиксированные настройка и запрос. Чтобы расширить выдачу по брифу, пользователь делает
   дополнительный запуск с включённым «Вторым шансом»; его результаты дополняют пул брифа.
   План запуска фиксирует фактический режим каждого условия.
4. Сложные переводы не делаем. Getmatch: категории специализаций (`sp`) не выбираем, профиль проверяем локально.
   **Обходится целиком лента — страницы списка, а не карточки.** Лимит страниц сохраняется, но по умолчанию покрывает
   всю ленту с запасом (934 публикации на 02.10.2026); страница — 100 публикаций (API принимает), то есть около
   10 запросов на всю ленту. Карточки запрашиваются только для прошедших фильтр по ленте (5.4), как у любого источника.
5. Простые нативные фильтры Getmatch используются по общим правилам (жёсткие всегда, мягкие — при выключенном
   «Втором шансе»). Параметры найдены в скриптах сайта и проверены на живом API 02.10.2026:

   | Параметр | Значения | Общее условие | Перевод |
   |---|---|---|---|
   | `l` (несколько) | `moscow`, `saints_p`, `regions_ru`, `relocate`, `remote` — объединение | Места + формат | Уже реализован; при включённом «Втором шансе» формат не сужает `l` |
   | `se` (несколько) | `junior`, `middle`, `senior`, `lead`, `c_level` — объединение | — | Не используется: фильтра грейда нет (3.5) |
   | `sa` | `any`, `150000`, `200000`, `250000`, `350000` ₽/мес | Зарплата | Наибольший порог не выше X, только для RUB/мес. Включать после проверки, что `sa` не отрезает вакансии без зарплаты и вилки с B ≥ X (3.5): по числам на 02.10.2026 вакансии со скрытой зарплатой остаются |
   | `pa` | `all`, `30d`, `7d`, `3d`, `1d` | Дата публикации | Наименьший период, который целиком покрывает «не раньше даты»; точная дата локально |
6. **Заявленные возможности должны быть настоящими.** Условие объявляется `native` или `local`, только если
   адаптер действительно может получить по нему и «подходит», и «не подходит». Условие, которое у источника
   всегда даёт один и тот же результат (например, всегда «неизвестно», потому что данных нет), объявляется `none`.
   Каждое заявленное `local` условие покрыто фикстурами, где оно даёт оба результата.
7. Объявление возможностей строится из реальных данных адаптера (какие поля он извлекает), а не пишется вручную отдельно от парсера.

## 5. Конвейер исполнения

### 5.1 Параллельность

- Источники работают **параллельно** и независимо.
- Внутри источника лимит одновременных запросов общий для всех этапов и всех запусков.
- **Каждая поисковая фраза обходится обязательно.** Лимит задаётся на фразу в источнике (вакансий и страниц), а не общий на запуск: исчерпание лимита одной фразой не отменяет другие.
- Фразы и нативные запросы одной фразы обрабатываются **с чередованием** (сначала первые страницы, потом вторые), чтобы ранние результаты были по всем фразам сразу.
- Источник без текстового поиска (Getmatch) обходится **один раз** на запуск, сколько бы фраз ни было.

### 5.2 Граф этапов (пример HH)

```text
лента HH (по каждой фразе) ──► предфильтр ──► карточка вакансии
                                                │
                     профиль работодателя HH ◄──┘ (один раз на работодателя)
                       │            │
                       │            └──► открытые вакансии работодателя на HH (только релевантные фразам)
                       ▼
          ссылка на сайт работодателя ──► сохранение и показ в карточке
```

Какие полезные сведения есть в профиле работодателя HH (кроме ссылки на сайт), нужно проверить на живых страницах: текущая фикстура урезана.

Другие источники — подмножество: Getmatch = лента → предфильтр → карточка (+ профиль компании, когда будет реализован).

Пользователь открывает сайт работодателя по сохранённой ссылке. Движок по ней не переходит.

### 5.3 Этап фильтрации

Фильтрация — **отдельный общий этап**, реализованный один раз и одинаковый для всех источников.
Источник фильтров не реализует: он только забирает данные (и передаёт нативные фильтры, раздел 4).
Даже простая первая версия фильтров (проверка профиля по названию, места, формат) — это отдельный этап, а не логика парсера.

Поток данных через хранилище:

```text
лента (с пагинацией) ──► запись вакансий в таблицу ──► фильтр по данным ленты
                                                          │ решает, какие карточки догрузить
                                                          ▼
                                   карточки ──► обновление записей ──► фильтр по полным данным
```

Порция обработки — **страница ленты**, а не вся лента целиком [предложение]: страница записана → отфильтрована →
её карточки ставятся в очередь, пока грузятся следующие страницы. Так сохраняется разделение этапов и при этом
первые полные карточки появляются через секунды, а не после окончания всей ленты.

### 5.4 Предфильтр и глубина

- Карточка автоматически запрашивается только у вакансий, которые по данным ленты не провалили ни жёстких, ни мягких условий.
- Провалившие мягкое условие по ленте попадают в «Может быть подходит» с данными ленты и ссылкой. Карточка загружается **по запросу пользователя**: при открытии вакансии в интерфейсе — одна задача через тот же лимит источника. После загрузки условия пересчитываются, и вакансия может перейти в «Подходит». Рядом — ссылка на оригинал на сайте источника.
- Профиль работодателя внутри источника — только для работодателей хотя бы одной вакансии, не скрытой по профилю.
- Открытые вакансии работодателя: только релевантные (на HH — поиск по фразам с фильтром работодателя), с отдельным лимитом на работодателя.

### 5.5 Дедупликация

Ключ каждой задачи: вакансия `source:id`, работодатель `source:employer_id`.
- Внутри запуска: одна задача на ключ, повторные находки только добавляют происхождение.
- **Происхождение сохраняется и показывается**: источник, точка входа (лента агрегатора, открытые вакансии работодателя внутри агрегатора), поисковая фраза, нативный запрос и страница — для каждой находки вакансии, а не только первой.
- **Между запусками ничего не делается повторно** (решение 02.10.2026). Лента обходится заново — иначе не увидеть новые вакансии.
  Полностью полученные данные берутся из базы без повторного запроса: карточка вакансии
  с очищенной HTML-разметкой описания, профиль работодателя. Карточка без разметки описания
  считается неполной и загружается при следующей находке (уточнение 08.10.2026). Повторное использование работает **по всем брифам пользователя**: данные вакансии одинаковы,
  а решение фильтров и статус пользователя у каждого брифа свои.
- Ошибка, капча, блокировка не сохраняются как полученные данные: следующий запуск попробует снова.

## 6. Источники, лимиты и ответы

### 6.1 Каталог и выбор источников

- `GET /sources` возвращает доступные источники: id, название, **тип**, возможности (способ применения каждого условия, этапы), текущее состояние (доступен / заблокирован: VPN, капча, breaker — с причиной и временем окончания паузы breaker).
- Подключённые источники имеют тип `aggregator` (HH, Getmatch); в будущем — `telegram` (каналы с вакансиями).
- Запуск принимает **список выбранных источников**; по умолчанию — все доступные. Выбранные источники работают в одном запуске параллельно.

### 6.2 Сетевая политика

- У каждого источника свои настройки: число одновременных запросов, интервал, таймаут, ретраи, breaker.
- Каждый источник **классифицирует ответ**, а не только HTTP-код:

| Класс | Пример | Ретрай | Действие |
|---|---|---|---|
| ok | Нормальная страница | — | — |
| retryable | 5xx, таймаут, 429 | Да, с паузой | Breaker после серии |
| vpn_blocked | HH: редирект на «отключите VPN» с кодом 200 | Нет | Остановить источник, сказать пользователю |
| captcha | Редирект/страница капчи | Нет | Breaker, сказать пользователю |
| not_found | Вакансия снята | Нет | Отметить вакансию |
| parse_error | Неожиданная разметка | Нет | Событие, вакансия с ошибкой |

### 6.3 Сбой одного источника

Решение 02.10.2026: приостановки и «Доискать» нет.
- Капча, VPN-редирект, 401/403 или открытый breaker → источник **заблокирован до конца запуска**: новые запросы к нему
  не отправляются, оставшиеся задачи отмечаются пропущенными. Решать капчу не пытаемся.
- Остальные источники и их этапы продолжают работу; запуск завершается статусом «частично» и списком заблокированных
  источников с причиной и подсказкой («отключите VPN»).
- Пользователь устраняет причину и делает новый запуск. Он не повторит уже сделанного: лента обходится заново,
  карточки и профили берутся из базы (5.5).
- Задачи хранятся только в памяти; при перезапуске сервиса незавершённый запуск помечается прерванным, сохранённые вакансии остаются.

## 7. Парсинг

- Из ленты извлекается **всё полезное**: от этого зависят выдача и качество предфильтра. Потеря поля из ленты — дефект.
  HH, обязательно: страна (корень `area.path`), город, адрес, профессиональные роли (`professionalRoleIds` — для профиля), формат, график, занятость, опыт, зарплата, дата.
- Из карточки — максимум: описание, навыки, формат, график, занятость, зарплата, опыт, адрес, сведения о работодателе.
- Каждая вакансия хранит нормализованные поля и исходные данные источника (`source_data`).
- Таблица соответствий значений (форматы, занятость, опыт) ведётся в адаптере и покрыта фикстурами.

## 8. Хранение: локально и Supabase

Решение от 01.10.2026: база знаний общая для всех пользователей, найденные вакансии хранятся в Supabase в разрезе пользователя, доступ — по авторизации.

| Где | Что | Доступ |
|---|---|---|
| Supabase, общее | Компании и их идентичности в источниках (HH employer id, Getmatch id, домен); ссылки на сайты; публичные сведения о компании; в будущем — списки компаний (3.6) | Читают все авторизованные; пишет движок любого пользователя |
| Supabase, пользователь | Брифы, пул брифа, статусы и пометки, найденные вакансии (своя копия у каждого пользователя), резюме, письма | Только владелец (row level security) |
| Локально | Очередь и состояние запуска, события и HTTP-журнал, кэш сырых ответов, настройки и лимиты источников, буфер записи при отсутствии сети | Только этот компьютер |

- Вакансии — **копия у каждого пользователя** (решение 01.10.2026). Общий корпус требует инфраструктуры, а повторная загрузка карточки нагружает источник, а не нас.
- Запись в общую базу от разных пользователей требует дедупликации компаний по идентичностям и защиты от мусора (минимум: кто и когда добавил, дата последней проверки).

## 9. Бриф как воронка

- У брифа **одна таблица вакансий** (пул). Задача запусков — наполнять её; пользователь работает с пулом, а не с отдельными запусками.
- Запуск добавляет в пул новые вакансии; уже известные отмечаются «снова найдена» (последний запуск и время) и получают новое происхождение.
- Папки воронки: все вакансии, неразобранные (новые и просмотренные), неинтересные,
  отправлен отклик, собеседование, отказ работодателя, оффер. Один текущий этап на вакансию;
  переходы допускаются в любом порядке. Отметка отклика не отправляет отклик работодателю.
  Статус и заметка не теряются при новых запусках.
- Показ по умолчанию: неразобранные, с любым решением автоматических фильтров.
  «Все вакансии» включает все этапы. Счётчики папок не зависят от фильтров текущего списка.
- Главная — таблица брифов. Внутри брифа — папки и компактный список по 50 вакансий,
  описание и заметка в области чтения с тем же левым краем, что и карточки списка. Настройки и история поиска — отдельные экраны.
  Сохранение настроек не запускает поиск; источники и лимиты сохраняются в брифе.
- Решение фильтров хранится в пуле и пересчитывается локально, без запросов к источникам: после каждого запуска
  для найденных вакансий и для всего пула при изменении условий брифа.
- Снимок каждого запуска (параметры и что он нашёл) сохраняется для истории и замеров.

## 10. Локальный веб-сервис, VPN, доставка

- Движок работает на компьютере пользователя: запросы идут с его IP, прокси не нужны.
- Конфликт с VPN: HH не работает с VPN, а агенту VPN может быть нужен. Движок определяет `vpn_blocked`, блокирует до конца запуска только этот источник и подсказывает, что сделать (6.3). Пользователю дополнительно подсказывается раздельное туннелирование (split tunneling) для доменов источников.
- Приложение — **локальный веб-сервис**: на компьютере пользователя работают и движок поиска, и сервер, который отдаёт интерфейс. Пользователь открывает его в браузере (`http://127.0.0.1:<порт>`).
- Supabase используется как внешнее хранилище (общая база знаний и данные пользователя) с авторизацией; интерфейс и движок обращаются к нему из локального сервиса.
- Доставка как у Label Studio: Python-пакет с уже собранным фронтендом внутри. `uv tool install <пакет>` (или `pipx`), затем `<пакет> start` поднимает сервис и открывает браузер. Node.js и Docker пользователю не нужны: фронт собирается при выпуске пакета.

## 11. Нефункциональные требования

### 11.1 Скорость поиска

Один запуск должен завершаться как можно быстрее. Верхнюю границу задают лимиты источников: их не нарушаем,
поэтому ускорение — это меньше лишних запросов и лучшая загрузка разрешённого бюджета, а не более частые запросы.

**Бейзлайн фиксируется до оптимизаций.**
- Набор эталонных сценариев: например, HH «QA» по Москве; бриф из трёх фраз; полная лента Getmatch; запуск нескольких источников сразу. Сценарии и их параметры хранятся в репозитории.
- Метрики каждого запуска:

  | Метрика | Зачем |
  |---|---|
  | Время до первой вакансии и до первой полной карточки | Когда пользователь начинает работать |
  | Полное время запуска | Итоговая скорость |
  | HTTP-запросы по этапам и источникам | Куда уходит бюджет |
  | Запросов на одну показанную вакансию | Доля лишней работы |
  | Время ожидания лимита и доля простоя разрешённых слотов | Упираемся в источник или в себя |
  | Время разбора и записи в базу | Собственные накладные расходы |

- Два вида замеров:
  - **живой**: реальные источники, разброс из-за сети, несколько повторов;
  - **офлайн**: подменённый транспорт с фикстурами и заданной задержкой ответа. Показывает накладные расходы движка без влияния сети, воспроизводим, годится для автоматической проверки на регрессии.
- Результаты бейзлайна записываются в `docs/` с датой и версией кода. Оптимизация принимается только со сравнением с бейзлайном на тех же сценариях.
- Офлайн-бейзлайн текущего движка: [baseline-2026-10-02.md](baseline-2026-10-02.md). Инструмент — `benchmarks/run.py`.
  После шага 2 (перестройка движка): [benchmark-step2-2026-10-02.md](benchmark-step2-2026-10-02.md).
- Прежние замеры из README (HH: 10 вакансий за 33,5 с; Getmatch: 11,9 с, 28.09.2026) — ориентир, но не бейзлайн: сценарии не зафиксированы.

Направления оптимизации, которые нужно оценить на бейзлайне:
- больше данных из ленты для предфильтра, чтобы не грузить лишние карточки (например, страна HH из `area.path`);
- дедупликация задач между фразами и точками входа (5.5);
- параллельная работа источников и полная загрузка лимита каждого;
- чередование фраз, чтобы лимит запуска не тратился на одну фразу;
- никаких запросов профилей работодателей для вакансий, скрытых по жёстким условиям;
- повторное использование карточек и профилей между запусками (5.5).

### 11.2 Качество кода

Код должен быть простым для понимания и следовать принципам чистой архитектуры и SOLID.
Чем проще прочитать и изменить, тем лучше; простота важнее универсальности.

Правила:
- **Одна ответственность у модуля и класса.** Планирование, планировщик задач, обработчики этапов, проверка условий, сохранение результатов, метрики и события — отдельные компоненты с понятными интерфейсами.
- **Направление зависимостей.** Модели и правила фильтров не зависят от сети, базы и FastAPI. Движок не знает конкретных источников; адаптеры не знают движка и базы.
- **Новый источник или этап добавляется без правки движка**: адаптер, его настройки, регистрация.
- **Типизированные данные между компонентами**: модели вместо вложенных `dict` (сейчас запуск передаётся как `run["request"]["brief"]["filters"]`).
- **Нет длинных функций с общим изменяемым состоянием в замыканиях.** Состояние запуска — явный объект; функция решает одну задачу.
- **Не дублировать логику**: одна точка для перевода значений источника, одна для дедупликации, одна для повтора запросов.
- **Проверки**: Ruff и Mypy в строгом режиме для всего `src` (сейчас Mypy проверяет только парсеры и фильтры, а на всём `src` даёт 40 ошибок); юнит-тесты для чистых частей; интеграционные тесты движка с подменённым транспортом.

Текущий `engine.py` этим требованиям не соответствует: `_pipeline` — одна функция примерно на 230 строк
с вложенными замыканиями, общими счётчиками и смешанными обязанностями (обход ленты, очередь карточек,
профили компаний, фильтрация, метрики, события). Его нужно разделить на компоненты из первого правила
в рамках перехода на конвейер из раздела 5.

### Уточнение устройства приложения от 08.10.2026

- `api/v1` принимает HTTP-запросы и получает операции приложения через `dependencies.py`.
- `services/` содержит операции брифов, вакансий, запусков, источников, географии и системной статистики.
- Изменение брифа и пересчёт решений по его пулу атомарны: при ошибке откатывается вся операция.
- `/api/v1/sources` описывает подключённые адаптеры и текущую локальную блокировку (`ready` / `blocked`).
  Получение этого списка не проверяет сайты. Реальная доступность отложена на вторую очередь;
  критерии и механизм проверки пока не выбраны.
- Общая география публикуется через `/api/v1/geography`; нативные справочники источников наружу не выдаются.
