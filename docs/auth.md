# Вход и общий каталог компаний

Вход нужен для чтения `public.company_links` в Supabase. Локальные брифы,
результаты и поиск HH/Getmatch продолжают работать без этого входа.

## Как войти

В браузере нажмите **«Войти»** в шапке приложения. Ассистент вызывает
`authorize()` без параметров и показывает полученный `login_url`.
Оба пути открывают `/auth`: страница показывает только включённые в Supabase
способы входа из поддерживаемых GitHub и Google. После выбора провайдера и входа
можно вернуться в приложение или к ассистенту. В шапке появятся имя и «Выйти».

Вызов `authorize()` возвращает `authenticated`, `user` и `login_url`.
При действующей сессии `login_url=null`. Этот вызов не начинает OAuth-попытку:
её время отсчитывается только после нажатия кнопки провайдера. Агенту не нужно
опрашивать статус: после подтверждения пользователя он вызывает `list_companies`.
После выхода этот инструмент возвращает ошибку 401 со ссылкой входа.

## Чтение каталога

`list_companies(name?, category?, specialization?, page=1, page_size=20)`
возвращает `{items, total, page, page_size}`. Размер страницы — от 1 до 100.
У страницы за концом каталога `items=[]`, а `total` сохраняет точное число строк.
`name` и `specialization` — поиск по части текста без учёта регистра,
`category` — точное вхождение отрасли в массив `categories`. Фильтры объединяются
условием «И». HTTP-эквивалент — `GET /api/v1/companies` с теми же параметрами.

У каждой строки есть `id`, `name`, `url`, `link_kind`, `provider`, `categories`
и `specialization`. Инструмент читает каталог; он не запускает обход этих сайтов.
Каталог не копируется в SQLite и не кэшируется между запросами.

## Каталог как источник вакансий

Строки каталога с поддерживаемым `provider` (`ats:greenhouse`, `ats:lever` и другие из
реестра `src/parsers/registry.py`) — сайты компаний, по которым можно искать. Они читаются
из Supabase в момент запроса с сессией пользователя: при выводе источников
(`GET /api/v1/sources`, `list_sources`) и при старте поиска. Локальной копии нет — владение
каталогом защищает его от копирования. Запуск хранит только id обойдённых досок
(например `ats:greenhouse:abbyy`) и их итоги. Бриф хранит правила источников и, если
пользователь выбрал компании, только их UUID (`company:<uuid>`), без адресов и названий
(`docs/brief-parameters/source-rules.md`).

Без входа или при сбое Supabase встроенные площадки работают как обычно. Ответ со списком
источников содержит `catalog.status` (`login_required`, `forbidden`, `unavailable`) и причину;
запуск отмечает сайты компаний пропущенными с пометкой «Сайты компаний доступны после входа» и ищет по остальным
источникам. Ошибка — только если искать не по чему.

MCP передаёт ассистенту описание инструмента и каждого параметра в `inputSchema`.
В описании `list_companies` указан инструмент для получения актуальных значений:

```python
get_company_filters()  # Категории, до 50 значений на странице.
get_company_filters(field="specialization", category="Корпоративное ПО", query="CRM")
list_companies(category="Корпоративное ПО", specialization="CRM", page_size=20)
```

`get_company_filters(field="category", category?, query?, page=1, page_size=50)`
возвращает `{field, items: [{value, link_count}], total, page, page_size}`.
`link_count` считает ссылки каталога, а `total` — разные значения после фильтрации.
Результаты упорядочены по убыванию количества ссылок, затем по значению.
Специализации остаются свободными описаниями; по подсказкам выбираются ключевые слова,
которые передаются в `list_companies`, а не длинные описания целиком.
`query` ищет буквальный фрагмент без учёта регистра. HTTP-маршрут —
`GET /api/v1/companies/filters`.

Условия `list_companies` выполняются в Supabase до пагинации. Для подсказок БД
отдельно группирует значения, применяет поиск и возвращает только нужную страницу;
клиент не скачивает каталог для локального отбора.

## Как хранится сессия

OAuth — вход через внешний аккаунт без передачи его пароля приложению.
Используется PKCE: одноразовый код можно обменять на сессию только с секретом,
созданным локальным сервисом для этой попытки. Обратный переход также привязан
к браузеру через HttpOnly-cookie и случайный `state`. Попытка действует 10 минут.
Перезапуск сервиса отменяет незавершённые попытки; готовая сессия сохраняется.

Пользовательские access/refresh tokens хранятся в `auth/session.json` внутри
каталога данных (`JOB_SEARCH_DATA_DIR`). Файл имеет права `0600`, каталог `0700`.
Это локальный файл, защищённый правами ОС, а не шифрованное хранилище.
Токены не возвращаются в MCP, браузер, URL или журналы приложения.
Перед истечением access token сервис обновляет его через refresh token;
одновременные запросы используют одно обновление. Временная ошибка сети сохраняет
сессию, отозванный refresh token требует повторного входа.

«Выйти» удаляет локальную сессию и отзывает её refresh token в Supabase
с `scope=local`. Другие устройства не разлогиниваются. При ошибке сети локальная
сессия всё равно удаляется, а интерфейс сообщает об ошибке удалённого выхода.
Повреждённый файл сессии можно удалить кнопкой «Сбросить вход» на странице входа.

## Настройка Supabase

В поставке есть только URL проекта и **publishable key**, предназначенный для
публичного клиента. Пароля базы и `service_role`/secret key в ней нет.
Параметры другого проекта: `JOB_SEARCH_AUTH__URL` и
`JOB_SEARCH_AUTH__PUBLISHABLE_KEY`. Secret/legacy keys отклоняются настройками.

Для справочника фильтров примените в SQL Editor миграцию
[`20261011_company_filter_options.sql`](../supabase/migrations/20261011_company_filter_options.sql).
Функция `company_filter_options` работает как `SECURITY INVOKER`: правила RLS
таблицы действуют от имени вызывающего пользователя. Право вызова есть только
у `authenticated`; функция выполняет только SELECT и не меняет данные каталога.
Клиент обращается к ней через `GET /rest/v1/rpc/company_filter_options`.
[Функции PostgREST поддерживают фильтры, подсчёт и пагинацию](https://docs.postgrest.org/en/stable/references/api/functions.html).

В Authentication → Sign In / Providers включите GitHub и/или Google и настройте
его OAuth-приложение. Callback провайдера — адрес Supabase
`https://<project-ref>.supabase.co/auth/v1/callback`, указанный в панели.
Страница приложения автоматически покажет подключённый поддерживаемый провайдер.
SMTP для этих способов входа не нужен; отдельного email-входа в приложении нет.

После провайдера Supabase возвращает пользователя на локальный адрес сервиса
`http://127.0.0.1:<port>/auth/callback?state=...`. Supabase Auth допускает loopback IP
для локальных клиентов. `localhost` при открытии `/auth` перенаправляется на
канонический `127.0.0.1`, чтобы браузер не терял cookie между разными именами.

Доступ к данным ограничивается в Supabase: включён RLS, роль `anon` не имеет
доступа, `authenticated` получает только SELECT. Политика чтения проверяет
`auth.uid() IS NOT NULL` и `auth.jwt()->>'is_anonymous' = 'false'`.
INSERT/UPDATE/DELETE не разрешаются. Клиент отправляет publishable key и
пользовательский Bearer token; скрытие кнопок не заменяет эти права.

Документация: [OAuth](https://supabase.com/docs/guides/auth/social-login),
[PKCE](https://supabase.com/docs/guides/auth/sessions/pkce-flow),
[API keys](https://supabase.com/docs/guides/api/api-keys).

## Проверка

Автоматические тесты: `uv run pytest -q tests/test_auth.py tests/test_mcp.py`.
Они проверяют контракт протокола с подменённым транспортом Supabase.
Для настоящей проверки откройте приложение, войдите, прочитайте каталог через
MCP, затем выйдите и повторите чтение: ожидается 401 со ссылкой входа.
Сохранять токены в отчёт или вводить их в чат для проверки не нужно.

Проверено 11 октября 2026 на установленном плагине 0.5.0: настоящий вход GitHub
из веб-интерфейса, та же сессия в MCP, 772 строки каталога, все три фильтра,
пустая выдача, выход и отказ в чтении после выхода. Вход сохранился после
перезапуска сервиса. Интерфейс проверен в Safari и Chrome, включая ширину 390 px;
ошибок консоли Chrome нет. Google в проекте выключен, его выбор проверен
автоматическим тестом с подменённым ответом Supabase, без настоящего Google-входа.

В тот же день на установленном плагине 0.5.1 проверен справочник через настоящий
MCP и Supabase: 44 значения категорий; для `Корпоративное ПО` + `CRM` — 3 разных
описания специализаций и 5 ссылок. Проверены отдельные страницы и пустая выдача,
отказ 401 без пользовательского токена, сохранение входа после обновления сервиса.
Все 377 автоматических тестов прошли. Отдельная проверка установленного пакета
без Python/uv в PATH подтвердила 20 MCP-инструментов и отказ в чтении справочника
до входа.
