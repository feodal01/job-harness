## Основной вывод

В v2 зарегистрировано **228 источников: 12 агрегаторов и 216 карьерных**. Последние состоят из трёх отдельных реализаций и 213 конфигураций работодателей на 22 метках платформ. Это не 228 независимых анкет.

У обычных карьерных сайтов действительно бывают категории, подразделения, офисы, типы занятости и пользовательские поля работодателя. Однако наличие параметра не означает, что его нужно обязательно заполнять. Необходимо различать:

1. **Общие условия брифа:** уже известны сервису, переводятся адаптером при наличии однозначного соответствия.
2. **Смысловой выбор:** например, нужные специализации. Может требовать агента.
3. **Необязательное сужение выдачи:** подразделения или команды; при доступной общей ленте можно оставить пустыми.
4. **Техническую настройку:** адрес доски, tenant, токены страниц, флаги получения данных; заполняет код источника.

В проверенных карьерных примерах дополнительный выбор не был обязательным для получения выдачи. Это не доказательство отсутствия обязательных полей у любого будущего карьерного сайта.

| Пример | Подтверждённое поведение | Кто должен исправлять |

## Зависимость от числа источников

Количество дополнительных заданий равно числу **неразрешённых смысловых решений**, а не числу сайтов или полей в их формах.

- Добавление 100 работодателей с доступной общей лентой может не добавить ни одного решения агенту. Число HTTP-операций при этом растёт.
- Добавление 100 работодателей, для которых действительно нужно выбирать местные подразделения/категории, может добавить 100 разных заданий даже на одной ATS. Одинаковая платформа не делает каталоги общими.
- Если без разбора отправлять все каталоги, объём растёт примерно как сумма их размеров. В четырёх живых примерах только каталоги заняли суммарно 10 031 символ. Это пример, а не прогноз для всего каталога v2.
- Если отправлять только неразрешённые поля, объём равен общему контексту плюс сумме схем и релевантных справочников выбранных заданий. Параллельность уменьшает ожидание, но не суммарный расход контекста моделей.
- Кэш справочника уменьшает сетевые запросы. Для уменьшения контекста нужно переиспользовать уже принятое решение и не отправлять справочник модели повторно без необходимости.

Для текущего прототипа HH+Getmatch достаточно одного блока смыслового выбора Getmatch в категорийном режиме. Staff.am и IT-Jobs.uz добавят максимум по отдельному выбору категории, если мы решим использовать такое сужение; технически у обоих есть более широкая стратегия. Большинство текущих карьерных реализаций можно первоначально переносить без дополнительных анкет, но не обещать полноту выдачи при достижении лимитов.

## Правила для будущего протокола

1. Возвращать `needs_input` только для решения, без которого нельзя исполнить выбранную стратегию с понятным охватом. Необязательные фильтры не превращать в обязательные вопросы.
2. У каждой стратегии явно указывать охват: общий список, текстовый поиск или выбранные категории. Отсутствие нативного фильтра не выдавать за отсутствие поддержки локальной проверки.
3. Уже известные общие условия переводить автоматически. Не отдавать агенту IDs пагинации, tenant, скрытые HTML-поля и флаги получения расширенных данных.
4. При малой полной ленте собирать её без выбора подразделений. Для больших лент решать вопрос бюджета, разбиения и допустимого сужения явно; не терять вакансии молча.
5. Переиспользовать схему платформы, но получать/кэшировать справочники по конкретной доске работодателя. Подготовленные решения сохранять в плане и перепроверять при изменении брифа или выбранных значений.
6. Сохранять основания выбора и диагностировать неподготовленный источник отдельно от пустой выдачи.
7. До переноса устранить ложное сужение в HH/VK/IBS и категорийных эвристиках, затем скрытые фильтры и потерю выходных данных. Новый визард не должен компенсировать эти дефекты дополнительными вопросами.

Движок и парсеры в рамках этого аудита не изменялись.

## Оценка дозаполнения при сборе небольших лент целиком

Это оценка целевого режима после исправлений, а не измеренная частота задач на репрезентативной выборке брифов. Общие требования считаются уже заполненными. Один блок выбора может покрывать несколько поисковых фраз; число заданий не умножается автоматически на число фраз.

| Группа | Источников | Ожидаемые дополнительные смысловые задания |
|---|---:|---|
| Getmatch | 1 | Один блок выбора специализаций из 49 вариантов для категорийного режима |
| Staff.am и IT-Jobs.uz | 2 | Ноль при поиске без категорий; до двух блоков, если явно выбираем такое сужение |
| Остальные агрегаторы | 9 | Ноль выявленных обязательных source-specific решений; общие условия переводит код |
| Карьерные источники | 216 | Ноль выявленных обязательных блоков для реализованных общих лент/текстовых запросов; локальные таксономии подключаются лишь при необходимости сужения |

Таким образом, базовый план по текущему каталогу можно готовить с **одним дополнительным заданием Getmatch**. Из уже обнаруженных категорийных механизмов возможны ещё два необязательных задания. Это не верхняя граница для будущей оптимизации всех крупных карьерных сайтов: их полные объёмы и стоимость загрузки деталей не измерены по всему каталогу.

Живые примеры 28.09.2026: Anyscale — 21 вакансия в одном ответе Ashby, чей API поддерживает передачу описания вместе с лентой; Snyk — total=23, Postman — total=36 в Workday. При размере страницы 20 для каждого из двух Workday хватило бы двух страниц ленты при неизменной выдаче. Вторые страницы и все детали в этом аудите не загружались. Workday требует отдельного уточнения полных карточек, поэтому две страницы ленты не означают два HTTP-запроса на весь поиск.

Полезно разделить стратегии:

- Если лента уже содержит полные тексты и укладывается в бюджет, собрать её целиком и применить общие проверки.
- Если лента краткая, собрать все её страницы в пределах бюджета, затем загружать детали кандидатов, не исключённых по достаточным фактам. При отключённых фильтрах такой отсев отсутствует.
- Для большой ленты использовать однозначно переводимые нативные параметры из брифа. Агент нужен только для неразрешённого смыслового выбора, например подходящего подразделения.
- Решение о полном сборе принимать по стоимости запросов и объёму ответа, а не только по числу вакансий: 100 записей с текстами в одном ответе могут стоить дешевле 30 отдельных карточек.

Порог полного сбора следует сделать настройкой после измерения запросов и времени. Его нельзя молча приравнивать к существующему `source_limit`: достижение лимита означает ограниченную полноту, а не полный обход работодателя.

## Уточнение после аудита: режим прототипа Getmatch

Решение от 28.09.2026: Getmatch в прототипе обходит общую ленту с пагинацией без `sp`. Оценка выше в один блок выбора относилась к ранее предложенному категорийному режиму. Теперь для HH+Getmatch требуется **ноль дополнительных заданий по выбору категорий**; география уже задана общими/доступными полями. Текст запроса Getmatch не применяет, фильтрация пока отсутствует. Результаты ограничиваются бюджетом сбора, достижение которого явно отмечается. Код v2 и исторические результаты аудита этим изменением не исправлены.
