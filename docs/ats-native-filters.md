# Серверные фильтры ATS

Серверный фильтр — параметр, который получает сайт ATS до выдачи вакансий. Локальный фильтр проверяет уже полученные вакансии по общим условиям брифа. Это разные этапы: локальная проверка продолжает работать после нативного поиска.

Исправление от 12 октября 2026 закрывает отдельный пробел из [отчёта на 105 компаний](../reports/ats-generalization-review-2026-10-12/reviewer/report.md): у всех 13 перечисленных платформ реализовано подтверждённое подмножество серверных фильтров. Это не исправление всех 19 замечаний того отчёта и не заявление о поддержке каждого варианта ATS.

## Контракт

`prepare(brief, fetch)` передаёт каждую фразу `BriefInput.queries` в нативный поиск там, где текст поддерживается. Параметры конкретного сайта задаются через `Board.native_filters`. Значения берутся из справочников и формы выбранной доски; идентификаторы категорий не выводятся из названия профессии.

```python
from src.parsers.ats.lever.parser import create_adapter
from src.parsers.ats.models import Board

source = create_adapter(Board(
    "https://jobs.lever.co/example",
    "Example",
    native_filters={"team": ["Engineering", "Product"], "location": "London"},
))
```

`source.capabilities.native_filters` перечисляет принимаемые параметры доски. Неизвестные имена и пустые значения вызывают ошибку, а не исчезают из запроса. Списки значений предназначены для параметров, допускающих несколько значений. Для Taleo доступность поля и его допустимые значения проверяются по форме конкретного работодателя; итоговые capabilities уточняются после подготовки.

Общие `SearchFilters` остаются независимыми от сайта. Их страна или формат удалёнки не превращаются автоматически в офис, подразделение или ограничение доступности вакансии на стороне ATS. У Breezy, Lever и JOIN фразы брифа по-прежнему проверяются локально; сервер получает явно выбранные категории.

## Реализованные запросы

| ATS | Серверный поиск | Дополнительные параметры `Board.native_filters` |
|---|---|---|
| Breezy | GET доски | `location` |
| Dreamjob | GET `jbfrp[text]` | — |
| Greenhouse | GET hosted route `keyword`, `_data=routes/$url_token` | — |
| iCIMS | GET `searchKeyword` | — |
| JazzHR | GET `q` | — |
| Jobvite | GET `/<tenant>/search?q=…` | — |
| JOIN | POST публичного GraphQL `publicJobs` с `companyId` | `categoryIds` |
| Lever | GET public postings API | `location`, `commitment`, `team`, `department`, `level` |
| SmartRecruiters | GET postings API, `q` | `country`, `region`, `city`, `department` |
| SuccessFactors RMK | POST `/services/recruiting/v1/jobs`, `keywords` | `locale`, `location`, `filter1`, `filter2`, `filter3`, `jobLocationCountry`, `jobLocationState`, `jobLocationCity`, `cust_WorkLocationType`, `rmeducationLevel` |
| Taleo Business Edition v2 | POST формы `jobSearch`, `keywords`, если поле существует | Поля `keywords`, `title`, `location`, `region`, `state` и обнаруженные `CUSTOM_<число>` |
| Teamtailor | GET `query` | — |
| Workable | POST `/api/v3/accounts/<slug>/jobs`, `query` | — |

Для Lever параметры сверены также с [официальным контрактом](https://github.com/lever/postings-api); для SmartRecruiters — с [документацией публичных endpoints](https://developers.smartrecruiters.com/docs/endpoints). Остальные используемые параметры подтверждены сохранёнными запросами интерфейсов провайдеров и живыми HTTP-проверками.

## Подготовка и страницы

Greenhouse использует hosted search для непустой фразы. Подробное описание выбранной вакансии загружается отдельным GET по ID. JOIN сначала получает ID компании с её публичной страницы, затем выполняет поиск в пределах этой компании. Публичный ID из URL JOIN отделён от внутреннего ID GraphQL.

SuccessFactors RMK требует публичный адрес `https://<карьерный-сайт>/search/`. Локаль читается со страницы либо задаётся явно. Старый `/career?company=…` остаётся XML-лентой без нативного текста. Автоматического перехода с XML-tenant на неизвестный домен RMK нет. RMK возвращает краткие карточки: описания и нормализованная география в этом варианте пока отсутствуют.

Taleo читает форму перед поиском и сохраняет её скрытые поля, `org`, `cws` и выбранные значения в POST каждой страницы. Если форма не содержит `keywords`, фразы не отправляются в выдуманное поле; план явно сообщает об этом. Остаются доступными подтверждённые поля, например `location`.

Следующие страницы сохраняют условия исходного запроса. Для JSON и form POST общий транспорт учитывает тип и содержимое тела в идентичности запроса, повторных попытках и перенаправлениях. iCIMS запрашивает ближайшую следующую страницу, чтобы не планировать повторно весь оставшийся диапазон.

## Проверка и границы

Регрессионные тесты сравнивают параметры фактически построенных запросов и ID из сохранённых положительных и нулевых ответов. Сжатые файлы `tests/fixtures/ats/native_filters/*.body.gz` содержат исходные байты HTTP-ответов; метаданные и SHA-256 находятся в `cases.json`. У сложных провайдеров примеры лежат в собственных каталогах `native_filters`, `native_live` и `native`.

Проверка настоящего SmartRecruiters-адаптера через `SearchEngine`, SQLite и тестовый HTTP-транспорт проходит две фразы и две страницы результата: 109 вакансий сохраняются, фильтр `q` остаётся в запросе второй страницы. Отдельные тесты проверяют JSON/form POST, повторные попытки, перенаправления и запрет выхода на чужой host.

Живые результаты и исходные запросы: [каталог проверки](../reports/ats-native-filters-2026-10-12/). Положительные и нулевые ответы отделены от проверки пагинации; сохранённый пример сам по себе не доказывает текущую доступность сайта.

```sh
uv run pytest -q
uv run ruff check src scripts tests benchmarks
uv run mypy
```

Обычный реестр приложения пока подключает HH и Getmatch. Изменение относится к библиотеке ATS-адаптеров; подключение каталога работодателей к поиску и пересборка установленного плагина остаются отдельным этапом.
