# Job Search Prototype

Локальный эксперимент: один FastAPI-процесс, одна SQLite-база, поиск по HH и Getmatch,
простой веб-интерфейс. Общие условия проверяются по ленте и повторно по полной карточке.
Исходный `qa-job-harness` для запуска не нужен.

## Плагин Codex

В репозитории есть Git-маркетплейс с плагином `job-search`. Пользователь добавляет
адрес опубликованного репозитория в маркетплейсы Codex, устанавливает **Job Search**
и начинает новый чат. Ручной запуск `start.command` не нужен. На первом обращении
плагин подготовит Python и зависимости, затем запустит сервис по запросу ассистента.
Пока репозиторий не опубликован, доступна установка из локального каталога.

Можно попросить: «Найди вакансии по моему брифу», «Открой мои результаты» или
«Останови сервис поиска вакансий». Сервис также выключается кнопкой в интерфейсе.
Он продолжает работать после закрытия чата; таймера простоя нет. Брифы и результаты
сохраняются отдельно от плагина и доступны после следующего запуска.

[Установка, устройство и проверка доставки](docs/plugin-delivery.md).

## Запуск из репозитория

На этом компьютере `uv` уже установлен. Он установит зависимости из `uv.lock`:

```sh
cd /Users/user/Documents/repos/hh-search-prototype
uv run python -m src
```

Открыть <http://127.0.0.1:8765>. На macOS также можно открыть `start.command`.
API: <http://127.0.0.1:8765/docs>. Остановка — кнопкой в интерфейсе или MCP-инструментом.
Docker, Node.js и сборка интерфейса для запуска не нужны.
`start.command`, `python -m src` и плагин используют один постоянный каталог данных
и переиспользуют работающий сервис. Команда печатает адрес и завершается; сервис
продолжает работать отдельно. Закрытие терминала его не останавливает.

Для разработки с отдельной базой и портом:

```sh
JOB_SEARCH_DATA_DIR="$PWD/data/dev" JOB_SEARCH_PORT=8766 ./start.command
```

Для запуска в переднем плане, с остановкой через Ctrl+C, используйте те же
переменные и `uv run python -m src.runtime`. Общая пользовательская база при этом
не затрагивается. Изоляция чатов и рабочих пространств в обычном режиме не применяется.

## Что можно попробовать

1. Создать бриф: название, запросы, заметки и общие фильтры.
2. Запустить поиск по одному или нескольким источникам сразу: они работают параллельно.
   Для HH каждая строка — самостоятельный запрос, обходятся все фразы по очереди страниц.
   Getmatch обходит общую ленту один раз: поисковые фразы для него необязательны и не применяются.
3. Смотреть карточки сразу после ленты; полный текст загружается отдельно, без ожидания конца поиска.
4. Открыть события поиска: HTTP-коды, время запросов,
   ожидание лимита, повторы, ошибки парсинга, завершение.
5. Открыть бриф из таблицы и работать с папками: все вакансии, неразобранные, неинтересные,
   отправленные отклики, собеседования, отказы и офферы. Вакансия открывается в области чтения, выровненной по левому краю списка:
   описание сразу под заголовком, закреплённая ссылка на оригинал и действия внизу.
   Карточка открывается нажатием по ней или кнопкой слева; соседние вакансии текущей страницы
   переключаются внутри области чтения. При возврате сохраняется позиция списка.
   «Отклик отправлен» и «Неинтересна» сохраняются одним нажатием; выбор другого этапа — сразу.
   Заметка раскрывается отдельно и сохраняется своей кнопкой. Статус переживает новые запуски.
6. Повторить поиск. Лента обходится заново, а уже загруженные карточки и профили работодателей
   берутся из базы и не запрашиваются повторно — в том числе для других брифов.
   Карточка считается полной, когда сохранена очищенная HTML-разметка описания.
   При следующей находке текстовая копия без разметки загружается заново; заметки и этапы сохраняются.
   Параметры и находки каждого запуска сохраняются снимками.
7. Остановить поиск. Полученные карточки остаются. После перезапуска сервиса
   незавершённый поиск будет помечен `interrupted`; очередь не восстанавливается.

Искомые профессии не зашиты в код. HH получает введённые запросы и регион,
Getmatch — только выбранную географию, без выбора специализаций.
Поиск HH выполняется по всем полям: попадание слова в описание тоже даёт результат.
Лимиты задаются на фразу в источнике: `max_items_per_query` — сколько новых уникальных вакансий
может дать фраза (включая отклонённые; дубликат из другой фразы лимит не расходует),
`max_pages_per_query` — страниц на каждый запрос фразы. Исчерпание лимита одной фразой не отменяет другие.
Значения по умолчанию — в настройках источника; запуск может их переопределить.

## Логирование

Сервис пишет единые логи приложения и HTTP-сервера в `service.log` рядом с базой.
При достижении 10 МиБ файл ротируется; сохраняются пять предыдущих файлов
`service.log.1`–`service.log.5`. Настройки — `log_max_bytes` и `log_backup_count`,
либо `JOB_SEARCH_LOG_MAX_BYTES` и `JOB_SEARCH_LOG_BACKUP_COUNT`.
`startup.log` содержит диагностику запуска до настройки логирования и заменяется
при следующем запуске процесса. Потоки процесса не перенаправляются в `service.log`.
В `settings.toml`: `log_level = "INFO"`, `log_format = "text"`; доступны уровни
DEBUG/INFO/WARNING/ERROR/CRITICAL и формат `json`. Переменные `JOB_SEARCH_LOG_LEVEL`
и `JOB_SEARCH_LOG_FORMAT` переопределяют файл.

Каждый HTTP-ответ содержит `X-Request-Id`; этот идентификатор связывает ответ с журналом.
Записи поиска содержат `run_id`, `source_id` и `stage`. Пишутся время, уровень, модуль,
статус и длительность запроса. Тела запросов, поисковые фразы и параметры URL в технические
логи не попадают. HTTP-запросы к источникам подробно журналируются на уровне DEBUG.
При встраивании `create_app` в другой сервер настройка вызывается явно через
`src.core.logger.configure_logging(settings)`.

Ожидаемые ошибки приложения переводятся в 404, 409 или 422. Неожиданные ошибки дают
500 с общим сообщением; тип исключения и стек остаются в журнале. Схемы успешных ответов
и ошибок опубликованы в `/docs`. Исторический `run.request` описан как JSON-снимок:
он хранит условия своего запуска, даже если текущая форма ввода уже изменилась.

├── schemas/               # схемы HTTP-ответов и параметры представления

HTTP-обработчики сгруппированы по ресурсам в `api/v1`. Общий роутер подключается
в `create_app`; обработчики получают сервисы через `Depends` из `src/dependencies.py`.
Сервисы выполняют операции приложения, движок управляет поиском, репозитории хранят данные.
`lifespan` создаёт зависимости и закрывает движок, HTTP-клиент и базу в обратном порядке,
включая ошибки запуска и завершения.
Сервисы можно вызывать без HTTP. Изменение брифа и пересчёт его пула выполняются
в одной транзакции: ошибка откатывает и условия, и решения по вакансиям.
Новый HTTP-ресурс добавляется отдельным роутером в `api/v1/router.py`.
Парсер и движок не зависят от FastAPI. Все API-маршруты начинаются с `/api/v1`;
интерфейс находится на `/`, Swagger — на `/docs`.

- `parsers/aggregators/hh/parser.py`: чистый парсер. Не обращается к сети, базе или FastAPI.
- `network/client.py`: HTTP-клиент, общий семафор и интервал, ретраи, Retry-After,
  простой breaker с периодом блокировки. Лента, карточки, профили и редиректы
  расходуют один бюджет HH, в том числе при нескольких одновременных поисках.
- `engine/`: компоненты с одной ответственностью.
  `coordinator.py` — запуск, параллельные источники, итоговый статус и дедлайн;
  `source_run.py` — один источник: план → лента → фильтр → карточки → профили, блокировка источника;
  `listing.py` — чередование фраз, пагинация и лимиты на фразу; `filter_stage.py` — единственное место
  вызова фильтров; `reuse.py` — уже полученные карточки и профили; `tasks.py` — одна операция на ключ
  для всех запусков; `recorder.py` — запись, события и метрики; `pool.py` — пересчёт решений пула.
  Очередь в памяти; при перезапуске незавершённый запуск помечается прерванным.
- `db/`: SQL разделён по репозиториям; они используют одно соединение и общую транзакцию.
  Новая база получает текущую ревизию Alembic. Существующие схемы 8 и 9 автоматически
  принимаются под управление Alembic после проверки структуры и создания копии в `backups/`.
  Ревизия хранится в `alembic_version`; старый журнал `schema_migrations` заменён.
  Все ожидающие миграции выполняются в одной транзакции; ошибка откатывает весь переход.
  Неизвестная ревизия или самовольно изменённая схема отклоняется без исправлений.
  [Порядок добавления миграций и восстановления](src/db/migrations/README.md).
  Исторические снимки запросов и предупреждения сохранённых брифов остаются данными.
  Таблицы: брифы, запуски (со статусом каждого источника), корпус вакансий, снимки находок запуска,
  пул брифа со статусами пользователя, происхождение находок, полученные профили работодателей,
  события, состояние ресурса. Сетевых запросов внутри транзакций нет.
- `models/`: компания, вакансия, бриф, фильтры и параметры запуска. `schemas/` описывает HTTP-ответы.
- `web/index.html`, `web/static/app.js`, `web/static/app.css`: интерфейс без JS-фреймворка и сборки.
  Главная — таблица брифов; у брифа отдельные экраны вакансий, настроек и истории поиска.
  Ссылки сохраняют папку, страницу, поиск и фильтры при перезагрузке и переходах назад/вперёд.
  «Поиск и условия» объединяет запросы, источники, лимиты и запуск поиска.
  «Сохранить и искать» повторно проверяет источники с первых страниц по всем текущим запросам;
  новые вакансии пополняют общую воронку, известные не дублируются. «Только сохранить» не запускает поиск.
- `core/config.py` + `settings.toml`: одна схема `pydantic-settings` и один файл значений.

### Источники и общая география

`GET /api/v1/sources` возвращает подключённые в `parsers/registry.py` адаптеры:
ID, название, тип, реализованные действия, поля, параметры поиска и состояние локальной блокировки.
`state.status=ready` означает, что локальная пауза после ошибок не действует; `blocked` — действует.
Это **не проверка доступности сайта**. Сетевых запросов при получении списка нет.
Реальная проверка доступности — вторая очередь, её устройство ещё не определено.
События вне запусков доступны через `GET /api/v1/sources/events?after=0`.

`GET /api/v1/geography/countries` и `/api/v1/geography/cities?country=RU&text=Москва`
читают локальный справочник. Подсказки не зависят от HH, Getmatch и соединения с интернетом.
В брифе сохраняются код страны, название города и регион, без ID источника.
При поиске каждый адаптер сам переводит эти значения в свои параметры; нативные справочники HH
используются только внутри адаптера и расходуют его общий сетевой бюджет.
Прежние ручки `/sources/{id}/countries`, `/sources/{id}/cities`, `/sources/{id}/regions`
удалены, а `/catalog/events` заменена на `/sources/events`.

Снимок [GeoNames](https://www.geonames.org/) от 08.10.2026 содержит 112 357 населённых пунктов
в 32 странах: `cities500` (население более 500 человек или административный центр).
Это не полный перечень всех поселений. Поиск учитывает русские и латинские названия,
регистр и диакритику, возвращает до 20 результатов; одноимённые места показываются с регионами.
Наличие города в общем справочнике не гарантирует его поддержку источником:
если HH не может однозначно сопоставить место, запуск показывает явную ошибку этого источника.
Описание данных, лицензия и команда воспроизводимой сборки — в [src/geography/README.md](src/geography/README.md).

### Возможности источника

`SourceAdapter` собирается из небольших компонентов. Обязателен только `search`;
`vacancy_details`, `company_profile` и `geography` подключаются при наличии реализации.
Тип (`aggregator`, `career_site`, `ats`, `telegram`) описывает источник для выбора и не определяет его методы.
Необязательная функция `classify` распознаёт ответы, которые HTTP-код не выдаёт: капчу HH (200),
в будущем — редирект «отключите VPN».
Пустых методов и отдельных флагов `supports_*` нет.

Все интерфейсы компонентов находятся в **`src/parsers/interfaces.py`**.
Реализации явно наследуют соответствующий `Protocol`; обязательные методы помечены
`abstractmethod`. `Search.prepare(brief, fetch)` переводит общий бриф в запросы и возвращает
`SearchPlan`: запросы, способы применения условий и пояснения. `build` получает
уже внутреннюю географию источника; её IDs не хранятся в общем брифе.
`tests/test_interfaces.py` запускает Mypy для всего `src/parsers`: проверяет сигнатуры,
типы атрибутов и сборку `SourceAdapter`. Аннотации методов обязательны.
Отдельно запустить проверку: `uv run mypy`.

| Компонент | Обязанность |
|---|---|
| `search.prepare/build/parse` | Перевод брифа, запросы, разбор ответа и пагинация |
| `vacancy_details.url/parse` | Уточнение вакансии по отдельной карточке |
| `company_profile.url/parse` | Сведения о компании из профиля внутри источника |
| `CountryCityGeography` | Справочник стран и подсказки городов (HH) |
| `RegionGeography` | Готовые варианты выбора региона/формата работы (Getmatch) |

Чистые парсеры не обращаются к HTTP, SQLite или FastAPI. Каждый запрос, включая
пагинацию и профиль компании, выполняет общий `Network`.
Очередь находится в памяти; нет сохраняемого графа или восстановления отдельных задач.

`GET /api/v1/sources` возвращает вычисленные возможности:

- `actions` — операции, для которых действительно подключены компоненты.
- `fields` — откуда может приходить поле: `search`, `vacancy_details`, `company_profile`.
  Это возможность извлечения, а не гарантия заполненности каждой вакансии.
- `query_parameters` — `native` (передаётся источнику), `mapped` (преобразуется,
  например в специализацию), `local` (требует нашей фильтрации), `unsupported`
  или `ignored` (поисковые фразы сохраняются в брифе, но источник обходит общую ленту).
- `query_notes` — объяснение смысла поиска пользователю и агенту.

`local` означает проверку общим модулем. Чего источник не умеет, то пропускается и записывается
в параметры запуска, а не блокирует его. Извлекаемая зарплата сама по себе не означает поддержку поиска по зарплате.
`company_profiles: true` включает профили там, где компонент есть; `false` отключает запросы,
пропущенное значение/null включает только реализованный компонент.

HH передаёт текст и регион в HTML-поиск; без поисковых фраз HH пропускается (`skipped`),
а если других источников в запуске нет, запуск возвращает 422.
Getmatch сразу запрашивает `/api/offers` без `sp` и обходит страницы общей ленты.
Несколько фраз в брифе не вызывают повторные обходы. Поле фраз сохраняется при переключении источника; интерфейс объясняет режим Getmatch; событие `search.query_skipped` сохраняет причину.
Getmatch не ограничивает ленту поисковыми фразами: результаты могут относиться к любым профессиям. Текстовые исключения из общих фильтров проверяются локально.
Выбранные регионы передаются повторяющимся параметром `l` на каждой странице.
Следующий offset вычисляется по `meta.offset + meta.limit`, а не по числу записей:
промопубликации могут добавляться сверх размера страницы. Обход заканчивается
на последней странице или при достижении лимита вакансий/страниц (`limited=true`).
Страница — 100 публикаций, вся лента (~930) — около 10 запросов.
Загрузка профиля компании Getmatch пока не реализована.
В общей ленте бывают промопубликации о найме сразу на несколько позиций.
Они сохраняются с исходным `offer_type`; их описания разбираются по отдельному шаблону.

**Текст ленты Getmatch — краткая выжимка.** Она сохраняется в `summary`, полный текст
из страницы вакансии — в `description`. Возможности источника отражают это различие.
Если карточка не загрузилась, выжимка сохраняется, ошибка видна, запуск имеет статус `partial`.

Движок сразу сохраняет результат ленты. При наличии компонента ставит карточку
на уточнение, иначе сохраняет `detail_status=not_required`. Отсутствие отдельного
запроса не означает наличия полного текста. Профиль компании запрашивается после карточки и только
для не отклонённых вакансий; одна ссылка — одна попытка за запуск, полученный профиль больше не запрашивается.
404 карточки означает снятую вакансию (`not_found`), а не ошибку источника.
Капча, 401/403 или открытый breaker блокируют источник до конца запуска (`blocked` с подсказкой);
остальные источники продолжают, запуск получает `partial`.
Лимиты, ретраи, breaker и события общие для всех операций источника и всех запусков.

В `run.started` есть снимок настроек и возможностей. `search.request` и `search.mapping`
показывают исходный запрос и реальные параметры обращения; `listing.parsed`,
`vacancy.saved`, `parse.*`, `http.*` показывают действия и ошибки. Метрики отдельно
считают страницы ленты, подготовительные запросы, загрузки карточек и полученные полные
описания. Время первого результата и первого полного описания измеряется отдельно.

Для нового источника нужны компоненты и настройки рядом с ним, поле в общей модели
`SourceSettings` и регистрация фабрики в `parsers/registry.py`. Движок и HTTP-клиент
не содержат ветвлений по имени источника. Один запуск обрабатывает выбранные источники параллельно;
несколько запусков могут идти одновременно. Вакансии имеют ключ `source:id`.

Одинаковый `resource` означает общий семафор, интервал и breaker. Разные политики
для одного ресурса отклоняются при создании движка. `allowed_hosts` ограничивает
HTTP-запросы и редиректы доменами источника и их поддоменами; это сетевая политика,
а не поисковый параметр HH. Обход внешних сайтов работодателей в требования не входит.

## Общие фильтры и география

В брифе хранится `filters`, без привязки к источнику. Страны — общий код (например `KZ`),
город — название и необязательный регион для различения одноимённых городов.
В начальном справочнике 32 страны; список находится в `geography/countries.py`.
`GET /api/v1/geography/countries` отдаёт список, `/geography/cities?country=RU&text=Москва` —
подсказки из справочника HH без выдачи его IDs пользователю. Вызовы HH используют общий лимит источника.
Город можно ввести текстом. HH разрешает его в ID перед поиском; неоднозначное или отсутствующее
соответствие завершает запуск явной ошибкой подготовки. Getmatch получает широкую категорию,
а конкретный город проверяется по структурированным данным.

Общие поля: `locations`, `minimum_work_format`, `employment`, `experience_years`,
`salary`, `published_after`, `relocation_support`, `excluded_companies`, `excluded_text`.
Формат задаётся одним минимально приемлемым значением: `office` → `hybrid` →
`remote_country` → `remote_worldwide`; более свободные форматы тоже подходят.
Места — альтернативы: офис/гибрид проверяются по городу и стране, удалёнка по стране —
по стране проживания, явно разрешённая удалёнка по миру — с учётом запретов стран.
Адрес офиса сам по себе не доказывает доступность удалёнки из другой страны.

Профиль из поисковых фраз, места и исключения — жёсткие условия: доказанное
несоответствие скрывает вакансию (`rejected`). Остальные условия мягкие: их нарушение
оставляет вакансию в группе «Может быть подходит» (`maybe`). Если нарушений нет,
итог — «Подходит» (`accepted`). Неизвестные и недоступные источнику сведения отдельно
отмечаются как «Не проверено» и не ухудшают итог. Профиль проверяется по названию и
навыкам с ограниченным словарём синонимов; неоднозначность не является причиной скрытия.

Предварительная оценка выполняется по ленте. Для `maybe` и `rejected` карточка
автоматически не запрашивается; остальные карточки уточняются и оцениваются повторно.
Оценка хранится в снимке запуска и отдельно в текущем пуле брифа. После изменения брифа
пул пересчитывается без сетевых запросов. История, пользовательские этапы и заметки сохраняются.
По умолчанию лента, счётчики и переходы между вакансиями исключают скрытые вакансии;
для проверки есть явный режим «Все, включая скрытые».

Настройка `second_chance` по умолчанию выключена. Выключенная настройка разрешает
безопасные нативные мягкие фильтры источников; включённая расширяет сбор, оставляя
мягкие условия для общей локальной проверки. Фактическое значение фиксируется в запуске.
HH передаёт поддерживаемые формат, опыт, занятость и дату; для географии строит запросы
по городу, удалёнке по стране и общей удалёнке. Getmatch использует `l` и дату `pa`.
Нативная зарплата пока не применяется: безопасность её отсечения не подтверждена.
Опыт и занятость Getmatch помечены недоступными, об этом предупреждает форма.
События `search.plan` и `filters.evaluated` показывают перевод условий и причины оценок.

Релокация означает **помощь работодателя с переездом**. Готовность кандидата переехать,
зарубежный офис и `l=relocate` не подтверждают помощь. Явные русские/английские формулировки
распознаются локально; условные, противоречивые и нераспознанные остаются непроверенными.

Пример тела `POST /api/v1/briefs`:

```json
{
  "name": "QA с помощью в переезде",
  "queries": ["QA", "тестировщик"],
  "filters": {
    "locations": [{"country": "KZ", "city": "Алматы"}],
    "minimum_work_format": "hybrid",
    "relocation_support": true,
    "salary": {"minimum": 500000, "currency": "KZT", "period": "month"}
  }
}
```

Зарплата сравнивается без конвертации валют и периода. Отсутствие зарплаты допускается;
для вилки сравнивается верхняя граница, для единственного «от» — указанная сумма.
Другая валюта или период дают «Не проверено». Строгий минимум и требование опубликованной
зарплаты удалены. `experience_years` — стаж кандидата: он должен быть не меньше минимального
требования вакансии. Грейд не используется как фильтр. Исключения компаний сравниваются
точно без регистра; текстовые исключения — фразами с границами слов, без морфологии и LLM.

Исторический перевод старых фильтров в схему 8 был выполнен разово.
Текущий механизм обновлений начинается со схемы 8; старый преобразователь не входит в приложение.

## Данные компаний

Отдельного справочника компаний пока нет: таблица `companies`, её API и вкладка
удалены ранее. Брифы, история поиска и снимки вакансий сохраняются.
Заполнение будущего справочника будет спроектировано отдельно.

Наблюдения об работодателе из ленты, карточки и отдельно загруженного профиля
сохраняются внутри вакансии и её снимка в запуске. При включённом `company_profiles`
профиль запрашивается один раз на работодателя и сохраняется в `company_profiles` (кэш, не справочник);
следующие запуски и брифы берут его оттуда. Ошибка профиля видна в событиях и не удаляет вакансии.
Местоположение компании не подменяет местоположение вакансии. Ссылки на сайты
компаний показываются в списке результатов и открытых карточках. Поиск контактов,
поиск карьерных разделов и загрузка или парсинг их лент в требования не входят.

## Настройки

Редактировать `settings.toml`. Перезапустить сервис после изменения.
Общие параметры — `database_path`, `run_timeout_seconds`, `max_active_runs`.
Параметры HH находятся в `[sources.hh_ru]`, Getmatch — в `[sources.getmatch]`.
Модели `HHSettings` и `GetmatchSettings` лежат рядом с парсерами и наследуют `RequestSettings`.
У каждого источника — лимиты на фразу `max_items_per_query`, `max_pages_per_query`
(HH: 50 и 2, Getmatch: 2000 и 15). У Getmatch есть дополнительный `page_size` (по умолчанию 100).
Движок использует настройки выбранного источника для числа обработчиков,
а его HTTP-клиент — для параллельности, интервала, таймаутов, повторов и breaker.

```toml
[sources.hh_ru]
concurrency = 2
interval_seconds = 1.5
request_timeout_seconds = 20
max_attempts = 2
retry_base_seconds = 1
breaker_threshold = 3
breaker_seconds = 30
geography_cache_seconds = 300
```

Одна корневая модель `pydantic-settings` собирает все настройки. Приоритет:
параметры конструктора → переменные окружения → TOML → значения модели.
Например, `JOB_SEARCH_RUN_TIMEOUT_SECONDS=300` или
`JOB_SEARCH_SOURCES__HH_RU__CONCURRENCY=3`. Частичное переопределение сохраняет
остальные поля секции. Опечатки и недопустимые значения отклоняются при запуске.

По умолчанию: 2 запроса HH одновременно, 1.5 секунды между стартами,
20 секунд на HTTP-запрос, 900 секунд на поиск, до 3 активных поисков,
2 попытки запроса. 429 учитывает Retry-After, 5xx и сетевые ошибки допускают
повтор с экспоненциальной задержкой и jitter. 403/captcha не обходятся.
Ограничитель сохраняет ближайшее разрешённое время запроса и паузу breaker в БД.

Запускать один процесс / один worker. Блокировка файла базы исключает двух
владельцев одной базы. Прототип не координирует лимиты с прежним движком
`job-harness` или с отдельно запущенным сервисом на другой базе.

## Границы эксперимента

Это проверка устройства будущего приложения, не перенос всего продукта.
Подключены только HH и Getmatch. Нет переходов на карьерные сайты, кэша ответов,
расписания поисков и резервного копирования по расписанию.
Автоматическая резервная копия создаётся перед изменением схемы существующей базы.
API работает только локально; сетевое многопользовательское размещение не предусмотрено.
События пока не удаляются автоматически. Одна ошибка детали сохраняет остальные
карточки и даёт `partial`; при неудаче до получения результатов будет `failed`.
Сохранённые результаты не означают, что источник выгружен полностью.

Для внешнего агента достаточно создать бриф через `POST /api/v1/briefs`, запустить
`POST /api/v1/runs`, затем читать `/api/v1/runs/{id}`, `/results` и `/events`.
В параметрах запуска указываются `"sources": ["hh_ru", "getmatch"]` (пусто — все) и при необходимости
`"limits": {"hh_ru": {"max_items_per_query": 20}}`. Вакансии брифа со статусами — `GET /api/v1/briefs/{id}/vacancies`,
статус — `PATCH /api/v1/briefs/{id}/vacancies/{key}`.

Ленты `/runs/{id}/results` и `/briefs/{id}/vacancies` возвращают объект
`{items, total, page, page_size, pages}`. Параметры: `page` от 1,
`page_size` от 1 до 100 (по умолчанию 50), `selection` — `all`, `candidates`,
`accepted`, `unknown` или `rejected`. У вакансий брифа есть также `status`:
`all`, `open` (новые и просмотренные), `new`, `viewed`, `dismissed`,
`applied`, `interview`, `rejected` (отказ работодателя), `offer`.
Этап `status` не зависит от автоматического решения `selection`.
Параметр `q` ищет в названии вакансии и компании без учёта регистра, `sort` задаёт порядок:
`first_seen` (по умолчанию), `newest`, `updated` (последнее изменение этапа).
`GET /briefs/{id}/vacancies/{key}` возвращает одну вакансию с описанием и заметкой.
`GET /briefs` дополнительно возвращает `funnel` (счётчики всех этапов без фильтров списка)
и `last_run`. Поле брифа `search` хранит `sources`, `limits`, `company_profiles` для следующих поисков.
Фильтры применяются ко всей ленте до пагинации. Порядок — от первых найденных
к последним, новые карточки добавляются в конец. Если запрошенная страница
больше последней, возвращается последняя; у пустой ленты `page=pages=1`.
Интерфейс показывает по 50 вакансий и загружает только открытую вкладку.
Агент по-прежнему составляет запросы сам; сервер не пытается интерпретировать
свободный текст заметки к брифу.
