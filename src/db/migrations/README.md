# Миграции SQLite через Alembic

Порядком обновлений управляет Alembic. `versions/` содержит Python-ревизии с
`revision`, `down_revision` и `upgrade()`. Текущая ревизия базы хранится в
`alembic_version`. Своего списка миграций или журнала контрольных сумм больше нет.
Репозитории приложения продолжают работать через `sqlite3`; ORM не добавлен.

## Запуск

При обычном запуске сервис автоматически обновляет базу до `head` перед приёмом
запросов. `Connection` удерживает файловую блокировку базы. Обёртка в `runner.py`:

1. Проверяет известность ревизии и соответствие структуры. Для старых схем 8/9
   проверяет исходную структуру, а для схемы 9 — также прежний журнал и checksum.
2. Перед изменениями проверяет целостность и ссылки, создаёт полную резервную
   копию через SQLite backup API, включая зафиксированные записи из WAL.
3. Для старой базы выполняет `alembic.command.stamp` только на проверенную исходную
   ревизию. Затем вызывает `alembic.command.upgrade(..., "head")`.
4. Выполняет принятие старой базы и все ожидающие ревизии в общей явной транзакции
   `BEGIN IMMEDIATE`. После обновления сверяет структуру, целостность и ссылки.
   Только после успеха фиксирует транзакцию; ошибка откатывает весь переход.

`env.py` получает готовое соединение через `Config.attributes["connection"]`.
Используется `transactional_ddl=True` и явное начало транзакции SQLAlchemy,
чтобы DDL SQLite не фиксировался отдельно от остальных изменений.
Основание: [рецепт Alembic](https://alembic.sqlalchemy.org/en/latest/cookbook.html#sharing-a-connection-across-one-or-more-programmatic-migration-commands)
и [транзакции SQLite в SQLAlchemy](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#enabling-non-legacy-sqlite-transactional-modes-with-the-sqlite3-or-aiosqlite-driver).

Для новой базы Alembic выполняет всю цепочку; резервная копия пустой базы не нужна.
Повторный запуск актуальной базы не выполняет обновления и не создаёт новую копию.
Неизвестная ревизия, неподдерживаемая старая схема и неожиданная структура
отклоняются без попытки автоматического ремонта.

## Переход со старого механизма

- `0008` — неизменяемая исходная схема из `../schema.sql`.
- `0009` — прежняя таблица `schema_migrations`; SQL сохранён в `legacy/` для проверки
  уже выпущенных баз и их старой контрольной суммы.
- `0010` — переход на учёт ревизий Alembic; прежний журнал удаляется. Брифы,
  результаты, этапы, заметки, исторические снимки и события не преобразуются.
- `0011` — брифы хранят правила источников вместо списка: из сохранённых брифов удаляется
  `search.sources`, они получают правила по умолчанию (`docs/brief-parameters/source-rules.md`).

`PRAGMA user_version=10` после перехода служит постоянной защитной меткой:
предыдущие версии приложения должны отклонять новую базу. Дальнейшие версии схемы
отслеживаются только Alembic; эту метку при добавлении ревизий увеличивать не нужно.
Код принятия схем 8/9 нужен для обновления пользователей выпусков 0.2/0.3.
Схемы старше 8 не поддерживаются. Обратных миграций с удалением данных нет.

## Работа разработчика

Из корня репозитория:

```sh
uv run alembic history
uv run alembic heads
uv run alembic revision -m "describe schema change"
```

Заполните `upgrade()` нового файла через `alembic.op`. Укажите линейную зависимость
от предыдущего `head`, сохраните пользовательские данные. Для перестройки таблицы
SQLite можно использовать `op.batch_alter_table`. Выпущенные ревизии не редактируйте.
Autogenerate не настроен: приложение не содержит SQLAlchemy metadata/ORM-моделей.

Для применения с блокировкой, резервной копией и проверками остановите сервис и выполните:

```sh
uv run python -m src.db.migrations
```

Команда использует общий каталог данных. Для временной базы разработки:

```sh
JOB_SEARCH_DATA_DIR="$PWD/data/dev" uv run python -m src.db.migrations
```

Прямые команды `alembic upgrade/stamp/downgrade` без подготовленного приложением
соединения отклоняются в `env.py`, чтобы не обходить резервное копирование и блокировку.
Не добавляйте в ревизии `COMMIT`, `ROLLBACK`, `VACUUM`, autocommit-блоки или
`sqlite3.executescript`: они нарушают общую транзакцию. Изменение данных выполняйте
через соединение, полученное от Alembic.

Проверяйте новую установку, поддерживаемые исходные версии, несколько ожидающих
ревизий, сохранность данных, резервную копию, повторный запуск и откат при ошибке
на промежуточном шаге. После изменения пересоберите пакет плагина.

## Восстановление

Остановите сервис и убедитесь, что процесс завершился. Сохраните проблемную базу
со всеми сопутствующими файлами отдельно. Восстановите выбранную копию
`backups/*.sqlite` как `search.sqlite` в каталоге данных; старые `-wal`/`-shm`
не должны оставаться рядом с восстановленным файлом. Запускайте совместимую версию
приложения. Перед повторной попыткой обновления исправьте причину ошибки.
Не копируйте только основной SQLite-файл работающего сервиса: последние записи
могут находиться в WAL.

Копии не удаляются автоматически. Они создаются перед обновлением схемы;
это не резервное копирование по расписанию. Управление данными через UI отложено.
